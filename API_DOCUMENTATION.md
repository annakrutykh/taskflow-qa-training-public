
# TaskFlow QA Training API v2.0

## 1. Общая информация

**TaskFlow QA Training API** --- учебный REST API для управления
проектами и задачами.

API предназначено для практики функционального тестирования REST API,
тестирования авторизации и ролевой модели, CRUD-операций, фильтрации,
поиска и сортировки, работы с PostgreSQL, проверки данных через DBeaver
и тестирования бизнес-логики и прав доступа.

### Технологии

-   FastAPI
-   PostgreSQL
-   SQLAlchemy
-   Pydantic
-   JWT Authentication
-   Docker / Docker Compose

### Base URL

`http://localhost:8000`

### Swagger UI

`http://localhost:8000/docs`

Все API-методы имеют префикс `/api/v1`.

## 2. Авторизация

API использует JWT Bearer Token.

Для работы с защищенными эндпоинтами пользователь должен:

1.  Выполнить регистрацию или использовать предустановленного
    пользователя.
2.  Выполнить `POST /api/v1/auth/login`.
3.  Получить `accessToken`.
4.  Передавать токен в защищенных запросах.

Формат заголовка: `Authorization: Bearer <accessToken>`.

Срок действия токена --- 8 часов. Если пользователь деактивирован,
доступ к защищенным ресурсам становится недоступен.

Если заголовок `Authorization` отсутствует, невалиден, просрочен, либо
пользователь деактивирован --- `401 Unauthorized`. Если токен валиден,
но прав недостаточно (например, не `ADMIN` на административной ручке)
--- `403 Forbidden`.

## 2.1 Формат ошибок

Любая ошибка возвращается в едином формате:

``` json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Task not found",
    "details": null,
    "correlationId": "b3c1e2d4-...",
    "timestamp": "2026-07-28T14:20:31.940Z"
  }
}
```

`correlationId` совпадает со значением заголовка ответа `X-Request-ID`
--- удобно передавать его в баг-репортах для сопоставления с логами
сервера.

## 2.2 Списки и пагинация

Все ручки, возвращающие список (`GET /users`, `GET /projects`,
`GET /tasks`, `GET /labels`, `GET /tasks/{task_id}/comments`), отдают
не голый массив, а обёртку:

``` json
{
  "items": [ /* элементы страницы */ ],
  "total": 42,
  "limit": 20,
  "offset": 0,
  "hasNext": true
}
```

`total` --- общее количество элементов без учёта `limit`/`offset`,
`hasNext` --- есть ли следующая страница. Элементы внутри `items` всегда
стабильно упорядочены (вторичный ключ `id ASC`), даже при явной
сортировке по другому полю --- это гарантирует, что пагинация не будет
"скакать" между страницами.

## 2.3 Заголовок `Location`

Любой успешный `201 Created` возвращает заголовок `Location` с адресом
созданного ресурса, например `Location: /api/v1/tasks/42`.

## 2.4 Health-check

`GET /health` --- всегда `200`, если процесс api жив. `GET /ready` ---
`200`, если приложение может выполнить запрос к БД, иначе `503`. Обе
ручки без префикса `/api/v1` и без авторизации.

## 3. Роли пользователей

  Роль      Описание
  --------- -----------------------
  `USER`    Обычный пользователь
  `ADMIN`   Администратор системы

Новый пользователь после регистрации получает роль `USER`.
Администратору доступны дополнительные операции управления
пользователями и метками, а также полный доступ к любому проекту и
задаче вне зависимости от участия в проекте.

## 3.1 Проектные роли

Доступ к проекту определяется участием в нём (таблица
`project_members`), а не глобальной ролью пользователя.

  Роль        Права
  ----------- ------------------------------------------------
  `VIEWER`    Просмотр проекта, задач, участников; комментарии
  `MANAGER`   + полный CRUD задач, привязка меток
  `OWNER`     + удаление проекта, управление участниками

Создатель проекта автоматически становится его `OWNER`. У проекта
всегда должен быть хотя бы один `OWNER` --- разжаловать или удалить
последнего `OWNER` нельзя (`409 LAST_PROJECT_OWNER`).

Пользователь, назначенный исполнителем задачи (`assigneeId`), но не
состоящий в участниках проекта, всё равно может просматривать эту
задачу, менять её `status` и оставлять комментарии --- но не может
менять `title`/`description`/`priority`, удалять задачу или
управлять метками.

Кто не является ни участником проекта, ни исполнителем задачи --- для
него ресурс выглядит как `404 Not Found`, а не `403` (чтобы не
раскрывать сам факт существования чужого проекта/задачи).

## 3.2 Удаление данных

`users`, `projects`, `tasks`, `comments` удаляются мягко (soft delete)
--- запись остаётся в БД, но помечается и перестаёт быть видна через
API. Удаление проекта каскадно "удаляет" его задачи и их комментарии.
После удаления пользователя его email снова доступен для регистрации.
`labels` удаляются физически (soft delete на них не распространяется).

Каждое мутирующее действие (создание/изменение/удаление ресурса)
пишется в таблицу `audit_log` --- отдельного REST-эндпоинта для чтения
журнала нет, смотрите таблицу напрямую через DBeaver.

## 4. Предустановленные данные

При запуске приложения выполняется сидирование базы данных. В БД
создаются тестовые пользователи (включая администратора и один
деактивированный аккаунт --- для проверки сценария логина
деактивированным пользователем), несколько проектов с разными ролями
участников и задачи, покрывающие все статусы и приоритеты.

Актуальные учетные данные указаны в `seed.py`.

После очистки Docker volume и повторного запуска приложения, либо
после `POST /api/v1/admin/reset` (раздел 10.1), начальные данные
создаются заново.

## 5. Auth

### POST `/api/v1/auth/register`

Регистрация нового пользователя. Авторизация не требуется.

#### Request Body

``` json
{
  "email": "user@example.com",
  "password": "Password123!",
  "firstName": "Ivan",
  "lastName": "Ivanov"
}
```

Ограничения: email должен быть валидным и уникальным; password --- 8--64
символа; firstName и lastName --- 1--50 символов.

Успешный результат: `201 Created`.

Возможные ошибки: `409` --- email уже существует; `422` --- ошибка
валидации; `429` --- слишком много попыток регистрации с этого IP
(см. раздел про rate limiting ниже).

### POST `/api/v1/auth/login`

Авторизация пользователя. Авторизация для вызова метода не требуется.

#### Request Body

``` json
{
  "email": "user@example.com",
  "password": "Password123!"
}
```

#### Response

``` json
{
  "accessToken": "<JWT_TOKEN>",
  "tokenType": "bearer"
}
```

Возможные ошибки: `401` --- неверные учетные данные; `422` --- ошибка
валидации; `429` --- слишком много попыток входа с этого IP (см. раздел
про rate limiting ниже).

### POST `/api/v1/auth/logout`

Отзывает текущий `accessToken` --- повторно воспользоваться им (в том числе
до истечения 8-часового срока действия) уже нельзя, даже если он ещё не
истёк. Тело запроса не требуется, токен передаётся как обычно в заголовке
`Authorization`.

Успешный результат: `204 No Content`.

Возможные ошибки: `401` --- не авторизован.

### Rate limiting на `/auth/login` и `/auth/register`

Обе ручки ограничены по количеству запросов с одного IP в течение
скользящего окна: по умолчанию 5 запросов/60 секунд для `/auth/login` и
10 запросов/60 секунд для `/auth/register`. При превышении лимита ответ ---
`429 Too Many Requests` с заголовком `Retry-After` (сколько секунд ждать
до следующей попытки). Задача этого лимита --- защита от перебора паролей
(brute force), а не от "обычного" трафика.

**Если тестируете `/auth/login` --- прочитайте перед началом.** Лимит
считает **любые** запросы к ручке, а не только неудачные попытки входа ---
в счётчик попадают и `422` (например, пустой пароль или невалидный
формат email). Если вы методично проверяете негативные сценарии (разные
некорректные тела запроса, граничные значения и т.д.), пять запросов
подряд закончатся раньше, чем вы ожидаете, и шестой вернёт `429`, даже
если это никак не связано с перебором пароля.

Что с этим делать:

- Это ожидаемое поведение, не баг --- проектируйте порядок тестов с учётом
  лимита (например, группами по 4--5 запросов с паузой), а не одним
  сплошным потоком.
- `POST /api/v1/admin/reset` **не снимает** эту блокировку --- он чистит
  только PostgreSQL, Redis не трогает.
- Единственный способ снять блокировку раньше `Retry-After` --- удалить
  соответствующий ключ `rate_limit:login:<ваш IP>` в Redis вручную (через
  `redis-cli` или Redis Commander, см. `docs/STUDENT_LOG_ANALYSIS.md`,
  раздел 6). Это необязательный инструмент курса, но если он у вас поднят
  --- быстрее, чем ждать минуту.

## 6. Users

### GET `/api/v1/users/me`

Получение данных текущего авторизованного пользователя. Доступ: `USER`,
`ADMIN`.

### PATCH `/api/v1/users/me`

Изменение имени и/или фамилии текущего пользователя.

``` json
{
  "firstName": "Petr",
  "lastName": "Petrov"
}
```

### GET `/api/v1/users`

Получение списка пользователей. Доступ только `ADMIN`.

Параметры: `limit` --- 1--100, по умолчанию 20; `offset` --- по
умолчанию 0. Ответ обёрнут в стандартную структуру списка (раздел 2.2).

### GET `/api/v1/users/{user_id}`

Получение пользователя по ID. Доступ только `ADMIN`. Ошибка `404`, если
пользователь не найден.

### PATCH `/api/v1/users/{user_id}/role`

Изменение роли пользователя. Доступ только `ADMIN`.

``` json
{
  "role": "ADMIN"
}
```

Допустимые значения: `USER`, `ADMIN`. Ошибка `409 LAST_ADMIN`, если это
последний активный `ADMIN` в системе, а роль меняется на `USER`.

### PATCH `/api/v1/users/{user_id}/status`

Изменение активности пользователя. Доступ только `ADMIN`.

``` json
{
  "isActive": false
}
```

После деактивации пользователь не может использовать защищенные методы
API. Ошибка `409 LAST_ADMIN`, если это последний активный `ADMIN`.

### DELETE `/api/v1/users/{user_id}`

Удаление пользователя. Доступ только `ADMIN`. Успешный результат:
`204 No Content`. Ошибка `409 LAST_ADMIN`, если это последний активный
`ADMIN` в системе (в дополнение к `409 LAST_PROJECT_OWNER`, если это
ещё и последний владелец какого-то проекта).

## 7. Projects

### POST `/api/v1/projects`

Создание нового проекта. Создатель автоматически становится участником
проекта с ролью `OWNER` (раздел 3.1).

``` json
{
  "name": "TaskFlow Backend",
  "description": "Разработка backend API"
}
```

Ограничения: name --- 1--100 символов; description --- до 1000 символов.

### GET `/api/v1/projects`

Получение проектов, в которых текущий пользователь состоит участником
(любая роль). `ADMIN` получает все проекты системы.

Параметры: `limit` --- 1--100, по умолчанию 20; `offset` --- по
умолчанию 0. Ответ обёрнут в стандартную структуру списка (раздел 2.2).

### GET `/api/v1/projects/{project_id}`

Получение проекта по ID. Доступ --- участник любой роли или `ADMIN`.

### PATCH `/api/v1/projects/{project_id}`

Обновление проекта. Доступ --- участник с ролью `MANAGER`/`OWNER` или
`ADMIN`.

``` json
{
  "name": "TaskFlow Backend v2",
  "status": "ARCHIVED"
}
```

Любое подмножество `name`, `description`, `status`
(`ACTIVE` | `ARCHIVED`).

### DELETE `/api/v1/projects/{project_id}`

Удаление проекта (soft delete, каскадно на его задачи и их
комментарии). Доступ --- участник с ролью `OWNER` или `ADMIN`.

Возможные ошибки: `403` --- участник, но роль ниже `OWNER`; `404` ---
не участник проекта, либо проект не существует (неразличимо). Успех:
`204 No Content`.

### POST `/api/v1/projects/{project_id}/members`

Добавление участника в проект. Доступ --- `OWNER` или `ADMIN`.

``` json
{
  "userId": 3,
  "role": "MANAGER"
}
```

`role` --- `OWNER` | `MANAGER` | `VIEWER`, по умолчанию `VIEWER`.
Успех: `201 Created`, заголовок `Location`. Ошибки: `404` --- проект
или пользователь не найден; `409 MEMBER_ALREADY_EXISTS` --- пользователь
уже участник.

### GET `/api/v1/projects/{project_id}/members`

Получение списка участников проекта. Доступ --- любой участник проекта
или `ADMIN`. Параметры и обёртка списка --- как везде (раздел 2.2).

### PATCH `/api/v1/projects/{project_id}/members/{user_id}`

Изменение роли участника. Доступ --- `OWNER` или `ADMIN`.

``` json
{
  "role": "MANAGER"
}
```

Ошибка `409 LAST_PROJECT_OWNER`, если это последний `OWNER` проекта.

### DELETE `/api/v1/projects/{project_id}/members/{user_id}`

Удаление участника из проекта. Доступ --- `OWNER` или `ADMIN`. Та же
защита `409 LAST_PROJECT_OWNER` на последнего `OWNER`. Успех:
`204 No Content`.

## 8. Tasks

### POST `/api/v1/tasks`

Создание задачи внутри существующего проекта. Доступ --- участник
проекта с ролью `MANAGER`/`OWNER` или `ADMIN`.

``` json
{
  "projectId": 1,
  "title": "Реализовать авторизацию",
  "description": "Добавить JWT авторизацию",
  "priority": "HIGH",
  "assigneeId": 2
}
```

Ограничения: title --- 1--100; description --- до 1000; priority ---
`LOW`, `MEDIUM`, `HIGH`; assigneeId --- ID
существующего пользователя или null (исполнителю не обязательно быть
участником проекта, раздел 3.1).

По умолчанию priority --- `MEDIUM`, статус новой задачи --- `TODO`.

Ошибки: `403` --- участник с ролью `VIEWER`; `404` --- проект не
найден (либо не участник) или `assigneeId` не существует.

### GET `/api/v1/tasks`

Получение списка задач с пагинацией, фильтрацией, поиском и сортировкой.
Ответ обёрнут в стандартную структуру списка (раздел 2.2).

Параметры: `limit`, `offset`, `status`, `priority`, `assigneeId`,
`projectId`, `search`, `sort`, `order`.

Статусы: `TODO`, `IN_PROGRESS`, `DONE`.

Приоритеты: `LOW`, `MEDIUM`, `HIGH`.

Поля сортировки: `createdAt`, `priority`, `title`, `status`.

Направление: `asc`, `desc`.

Пример:
`GET /api/v1/tasks?status=TODO&priority=HIGH&sort=createdAt&order=desc`.

Неизвестное поле `sort` приводит к `400 Bad Request`.

### GET `/api/v1/tasks/{task_id}`

Получение задачи по ID. Доступ --- участник проекта любой роли,
исполнитель задачи (`assigneeId`) или `ADMIN`.

Ответ включает поле `labels` --- список меток, привязанных к задаче:

``` json
{
  "id": 1,
  "projectId": 1,
  "title": "Создать регистрацию",
  "status": "TODO",
  "priority": "HIGH",
  "labels": [{ "id": 1, "name": "backend" }]
}
```

Ошибки: `404` --- задача не найдена либо доступа нет (неразличимо,
раздел 3.1).

### PATCH `/api/v1/tasks/{task_id}`

Частичное обновление задачи. Набор доступных для изменения полей
зависит от роли:

- `MANAGER`/`OWNER`/`ADMIN` --- любое из `title`, `description`,
  `status`, `priority`, `assigneeId` (переназначение или снятие
  исполнителя; `null` снимает, несуществующий `assigneeId` --- `404`).
- Исполнитель без членства в проекте --- только `status`.
- `VIEWER` --- ничего (любой PATCH вернёт `403`).

``` json
{
  "status": "IN_PROGRESS",
  "priority": "HIGH"
}
```

Если в теле запроса присутствует поле, недоступное вызывающему для
изменения --- `403 FORBIDDEN` с перечнем этих полей в `message`.

### DELETE `/api/v1/tasks/{task_id}`

Удаление задачи. Доступ --- участник проекта с ролью `MANAGER+` или
`ADMIN`. Успех: `204 No Content`.

## 9. Comments

### POST `/api/v1/tasks/{task_id}/comments`

Добавление комментария к задаче.

``` json
{
  "text": "Задача взята в работу"
}
```

Длина текста: 1--500 символов. Автор определяется по JWT-токену.

### GET `/api/v1/tasks/{task_id}/comments`

Получение комментариев задачи. Пользователь должен иметь доступ к
задаче.

Параметры: `limit` --- 1--100, по умолчанию 20; `offset` --- по
умолчанию 0. Ответ обёрнут в стандартную структуру списка (раздел 2.2).

### PATCH `/api/v1/tasks/{task_id}/comments/{comment_id}`

Изменение текста комментария. Доступ --- только автор.

``` json
{
  "text": "Исправленный текст"
}
```

### DELETE `/api/v1/tasks/{task_id}/comments/{comment_id}`

Удаление комментария (soft delete). Доступ --- автор комментария либо
участник проекта с ролью `MANAGER`/`OWNER` или `ADMIN` (модерация).
Успех: `204 No Content`.

## 10. Labels

### POST `/api/v1/labels`

Создание метки. Доступ только `ADMIN`.

``` json
{
  "name": "backend"
}
```

Длина имени: 1--30 символов. Название уникально. Ошибка `409`, если
метка уже существует.

### GET `/api/v1/labels`

Получение списка меток. Доступ любому авторизованному пользователю.

Параметры: `limit` --- 1--100, по умолчанию 20; `offset` --- по
умолчанию 0. Ответ обёрнут в стандартную структуру списка (раздел 2.2).

### DELETE `/api/v1/labels/{label_id}`

Удаление метки целиком (физическое, вместе со всеми привязками к
задачам). Доступ только `ADMIN`. Успех: `204 No Content`.

### POST `/api/v1/tasks/{task_id}/labels/{label_id}`

Добавление существующей метки к задаче. Доступ --- участник проекта с
ролью `MANAGER+` или `ADMIN` (исполнитель без членства и `VIEWER` ---
`403`). Повторное добавление не создает дубликат связи. Успех:
`204 No Content`.

### DELETE `/api/v1/tasks/{task_id}/labels/{label_id}`

Отвязка метки от задачи. Доступ --- участник проекта с ролью
`MANAGER+` или `ADMIN`. Идемпотентно (если метка не была привязана ---
всё равно `204 No Content`).

## 10.1 Admin

### POST `/api/v1/admin/reset`

Полностью очищает базу данных и заполняет её заново предустановленными
данными (раздел 4). Доступ только `ADMIN`. Необратимо --- все текущие
данные будут потеряны. Успех: `204 No Content`.

Удобно использовать между тестовыми прогонами, чтобы вернуть систему в
известное начальное состояние без перезапуска контейнеров.

## 11. Основные HTTP-коды

Тело любой ошибки — в едином формате, см. раздел 2.1.

  Код                          Значение
  ---------------------------- ------------------------------------
  `200 OK`                     Запрос успешно выполнен
  `201 Created`                Ресурс создан
  `204 No Content`             Операция выполнена без тела ответа
  `400 Bad Request`            Некорректный запрос
  `401 Unauthorized`           Ошибка авторизации
  `403 Forbidden`              Недостаточно прав
  `404 Not Found`              Ресурс не найден
  `409 Conflict`               Конфликт данных
  `422 Unprocessable Entity`   Ошибка валидации

## 12. Основные сущности БД

Таблицы PostgreSQL: `users`, `projects`, `project_members`, `tasks`,
`comments`, `labels`, `task_labels`, `audit_log`.

Основная связь: `User → Project → Task → Comment`.

`User` и `Project` связаны many-to-many через `project_members` (с
дополнительным полем `role`). `Task` и `Label` связаны many-to-many
через `task_labels`. `audit_log` --- независимый журнал мутирующих
действий (раздел 3.2).

## 13. Рекомендуемый сценарий начала работы

1.  Выполнить `POST /api/v1/auth/login`.
2.  Получить `accessToken`.
3.  Авторизоваться в Swagger через **Authorize**.
4.  Проверить пользователя через `GET /api/v1/users/me`.
5.  Создать проект через `POST /api/v1/projects`.
6.  Создать задачу через `POST /api/v1/tasks`.
7.  Проверить получение, фильтрацию и сортировку задач.
8.  Добавить комментарий.
9.  Получить список меток и добавить метку к задаче.
10. Для административных методов авторизоваться под пользователем с
    ролью `ADMIN`.

## 14. Практические задания

Раздел 13 показывает, как *воспользоваться* API. Ниже — маршрут для того,
чтобы его *протестировать*: от одной ручки без зависимостей до сценариев,
затрагивающих несколько ролей и связанных сущностей. Каждый следующий этап
опирается на функциональность, открытую на предыдущем, и использует уже
полученные навыки.

Как пользоваться разделом:
- используйте `docs/API_SPEC.md` как источник ожидаемого поведения — раздел
  описывает, *что* тестировать, а не *как это должно работать*;
- для общего подхода к тест-дизайну по методу (GET/POST/PATCH/DELETE) — см.
  `docs/reference/how-to-test-http-methods.md`;
- найденные расхождения оформляйте по `docs/STUDENT_BUG_REPORTING.md`.

### Этап 1. Регистрация и аутентификация

**Цель.** Освоить работу с самой независимой от остального API парой ручек
и получить рабочий `accessToken` для всех дальнейших этапов.

**Эндпоинты.** `POST /api/v1/auth/register`, `POST /api/v1/auth/login`,
`POST /api/v1/auth/logout`.

**Ссылки на спецификацию.** `docs/API_SPEC.md`, разделы 2 (Аутентификация)
и 6.1 (Auth) — включая правило разделения 401/403/404 и таблицу лимитов
запросов.

**Как тестировать.** `docs/reference/how-to-test-http-methods.md`, раздел
POST — для регистрации; раздел, применимый к операциям без изменяемого
состояния (аутентификация не создаёт ресурс в привычном смысле) — для входа.

**Задание.** Исследуйте работу регистрации нового пользователя и входа в
систему. Определите позитивные и негативные сценарии. Исследуйте
ограничения входных данных. Проверьте корректность обработки ошибок.
Проанализируйте, как ведёт себя система при выходе и последующей попытке
воспользоваться уже недействительным токеном.

**Ожидаемый результат.** Уверенное владение получением и использованием
`accessToken`; понимание, чем регистрация отличается от входа с точки
зрения тестирования; сформированные баг-репорты по найденным расхождениям
(если они есть).

---

### Этап 2. Профиль текущего пользователя

**Цель.** Научиться тестировать ручки, зависящие от того, *кто* делает
запрос, а не от параметров запроса.

**Эндпоинты.** `GET /api/v1/users/me`, `PATCH /api/v1/users/me`.

**Ссылки на спецификацию.** `docs/API_SPEC.md`, раздел 6.2 (Users).

**Как тестировать.** `docs/reference/how-to-test-http-methods.md`, разделы
GET и PATCH.

**Задание.** Исследуйте, как ручки `/me` реагируют на разные состояния
авторизации, полученные на предыдущем этапе. Определите, какие поля
профиля можно изменять, а какие — нет, и что происходит при попытке
изменить остальные. Проверьте корректность обработки ошибок при частичном
обновлении.

**Ожидаемый результат.** Понимание разницы между чтением и частичным
изменением ресурса, привязанного к текущему пользователю, без явного ID
в пути.

### Этап 3. Управление пользователями (роль ADMIN)

**Цель.** Освоить тестирование ролевого доступа — первый эндпоинт, где
результат явно зависит от роли вызывающего.

**Эндпоинты.** `GET /api/v1/users`, `GET /api/v1/users/{user_id}`,
`PATCH /api/v1/users/{user_id}/role`, `PATCH /api/v1/users/{user_id}/status`,
`DELETE /api/v1/users/{user_id}`.

**Ссылки на спецификацию.** `docs/API_SPEC.md`, разделы 3 (Ролевая
модель — глобальные роли) и 6.2 (Users).

**Как тестировать.** `docs/reference/how-to-test-http-methods.md`, разделы
GET, PATCH и DELETE.

**Задание.** Исследуйте, как одни и те же ручки ведут себя под пользователем
с ролью `USER` и с ролью `ADMIN`. Определите позитивные и негативные
сценарии для изменения роли и статуса другого пользователя. Проанализируйте
ответы сервера при попытке выполнить административное действие без нужных
прав. При необходимости проанализируйте логи приложения.

**Ожидаемый результат.** Навык проверки авторизации *и* прав доступа как
двух разных, последовательных проверок — валиден ли токен, и достаточно ли
прав именно для этого действия.

### Этап 4. Проекты и участники

**Цель.** Перейти от одиночных ресурсов к ресурсу с собственной ролевой
моделью и вложенной коллекцией участников.

**Эндпоинты.** Все ручки `/api/v1/projects` и `/api/v1/projects/{project_id}/members`.

**Ссылки на спецификацию.** `docs/API_SPEC.md`, разделы 3 (Проектные роли)
и 6.3 (Projects).

**Как тестировать.** `docs/reference/how-to-test-http-methods.md`, разделы
POST, GET, PATCH и DELETE.

**Задание.** Исследуйте создание проекта и то, что происходит с его
создателем автоматически. Определите позитивные и негативные сценарии
работы с участниками проекта для каждой из проектных ролей. Исследуйте
ограничения, связанные с последним владельцем проекта. Убедитесь, что
удаление проекта корректно отражается в базе данных — включая связанные
сущности.

**Ожидаемый результат.** Умение строить тестовые сценарии для ресурса, где
права зависят не от глобальной роли, а от роли внутри конкретного
экземпляра ресурса.

### Этап 5. Задачи

**Цель.** Проверить ресурс, доступ к которому определяется несколькими
независимыми путями (участие в проекте и назначение исполнителем), и
освоить тестирование фильтрации/сортировки/пагинации на практике.

**Эндпоинты.** Все ручки `/api/v1/tasks`.

**Ссылки на спецификацию.** `docs/API_SPEC.md`, разделы 3 (Доступ
исполнителя, Разрешение доступа к задаче) и 6.4 (Tasks).

**Как тестировать.** `docs/reference/how-to-test-http-methods.md`, разделы
POST, GET и PATCH — уделите особое внимание пунктам про фильтрацию,
сортировку и пагинацию.

**Задание.** Исследуйте создание задачи в проекте, полученном на прошлом
этапе. Определите, какой набор действий доступен участнику проекта в
разных ролях и отдельно — исполнителю, не входящему в проект. Исследуйте
параметры получения списка задач и их комбинации. Проверьте корректность
обработки ошибок при некорректных параметрах запроса. Убедитесь, что
изменения задачи корректно отражаются в базе данных.

**Ожидаемый результат.** Способность самостоятельно спроектировать матрицу
проверок «роль × действие» для ресурса с несколькими путями доступа.

**Задание.** Исследуйте добавление комментария к задаче, созданной на

сценарии привязки и отвязки метки от задачи. Проверьте поведение при
повторной операции над уже привязанной/отвязанной меткой.

**Ожидаемый результат.** Навык разделения прав доступа внутри одной группы
ручек по типу операции, а не только по ресурсу целиком.
