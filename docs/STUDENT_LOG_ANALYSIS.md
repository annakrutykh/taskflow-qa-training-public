# Работа с логами (Kibana) — необязательный, но полезный инструмент

⚠️ **Kibana не обязательна для прохождения курса.** Всё обучение можно пройти
через Swagger, Postman, PostgreSQL и сам API — без единого захода в Kibana.
Этот документ — для тех, кто хочет попробовать инструмент, которым реально
пользуются QA/DevOps в компаниях для расследования инцидентов: искать не
"что вернул мой запрос", а "что вообще происходило на сервере".

---

## 1. Что логируется

Каждый HTTP-запрос к API пишется одной строкой в structured-JSON формате и
уходит в Elasticsearch. Поля:

| Поле | Значение |
|---|---|
| `timestamp` / `@timestamp` | время события |
| `correlationId` | request ID (UUID) — тот же, что в заголовке ответа `X-Request-ID` и в теле любой ошибки |
| `level` | `INFO` / `WARNING` / `ERROR` |
| `logger` | какой логгер записал (`app.request` — почти всегда) |
| `message` | текст сообщения (`"request completed"` для обычных запросов) |
| `method` | HTTP-метод |
| `path` | путь ручки |
| `statusCode` | код ответа |
| `durationMs` | время обработки в миллисекундах |
| `clientIp` | IP клиента |
| `userId` | id авторизованного пользователя (если есть) |
| `username` | email авторизованного пользователя (если есть) |

Правило простое: `level` зависит от `statusCode` — `2xx/3xx` → `INFO`, `4xx`
(включая `401`, `404`, `422`, `429`) → `WARNING`, `5xx` и необработанные
исключения → `ERROR`. Отдельного поля "тип события" нет — успешная
регистрация это просто `POST /api/v1/auth/register` со `statusCode: 201`,
неуспешный логин — `POST /api/v1/auth/login` со `statusCode: 401`, и т.д.
Это реалистично: в реальных системах вы точно так же ищете события по
методу/пути/коду, а не по готовым ярлыкам.

## 2. Как открыть Kibana

1. Убедитесь, что стек поднят: `docker compose up --build` (или `-d`).
2. Откройте в браузере `http://localhost:5601`.
3. **Первый запуск стека может занимать до 1-2 минут**, пока Elasticsearch и
   Kibana инициализируются — если видите ошибку сразу после `docker compose
   up`, подождите и обновите страницу.

### Первоначальная настройка (один раз)

1. Слева откройте меню (☰) → **Discover**.
2. Если попросит создать **Data View** — укажите шаблон индекса
   `taskflow-logs-*`, поле времени `@timestamp`.
3. Готово — теперь видно все логи за всё время работы текущей сессии
   (данные не переживают `docker compose down -v`, см. README).

## 3. Как искать

Строка поиска в Discover понимает простой синтаксис `поле:значение`, можно
комбинировать через `AND`/`OR`.

| Задача | Запрос в Discover |
|---|---|
| Все запросы | (оставить поле поиска пустым) |
| Ошибки 500 | `statusCode:500` |
| Ошибки 404 | `statusCode:404` |
| Ошибки 401 | `statusCode:401` |
| Rate limit (429) | `statusCode:429` |
| Все ошибки клиента | `statusCode >= 400 and statusCode < 500` |
| Все ошибки сервера | `statusCode >= 500` |
| Запросы конкретного пользователя | `userId:5` или `username:"ivan@example.com"` |
| Неуспешные попытки входа | `path:"/api/v1/auth/login" and statusCode:401` |
| Конкретный запрос по request_id | `correlationId:"<значение из X-Request-ID>"` |
| Необработанные исключения | `logger:"app.error"` |
| Медленные запросы | `durationMs > 500` (порог — пример, подберите свой) |

Чтобы найти `correlationId` для конкретного запроса — возьмите значение
заголовка `X-Request-ID` из ответа (виден в Swagger/Postman/`curl -i`) или
из тела любой ошибки (поле `correlationId`).

## 4. Учебные задания

Выполните после того, как сгенерируете себе трафик через Swagger/Postman
(десяток-другой разных запросов, включая намеренно "плохие"):

1. **Найдите все ваши неуспешные попытки входа** за сессию — сколько их и
   с какими email вы пытались войти?
2. **Спровоцируйте `429`** (несколько быстрых запросов подряд на
   `/auth/login`) и найдите этот момент в логах — сколько запросов прошло
   до блокировки?
3. **Возьмите `X-Request-ID`** из любого ответа с ошибкой `4xx` и найдите
   именно эту запись по `correlationId` — совпадают ли `method`/`path` с
   тем, что вы реально отправляли?
4. **Найдите самый медленный запрос** за сессию (сортировка по
   `durationMs`) — какая это ручка и логично ли, что она самая медленная?
5. **Посчитайте**, сколько всего запросов сделал конкретный пользователь
   (`userId`) — воспользуйтесь количеством строк в Discover после фильтра.
6. (Продвинутое) Найдите в логах побочный эффект одного из ваших багов
   из `docs/STUDENT_BUG_REPORTING.md` — например, лишнее поле, странный
   код ответа или подозрительное содержимое `message` — это тоже
   допустимое доказательство в баг-репорте, приложите скриншот/выдержку.

---

## 5. Если Kibana не открывается

- Дайте ей 1-2 минуты после `docker compose up` — Elasticsearch и Kibana
  стартуют дольше, чем API/PostgreSQL.
- `docker compose ps` — `elasticsearch` и `kibana` должны быть `Up`.
- Если что-то пошло не так — проще всего `docker compose down -v` и
  `docker compose up --build` заново, чем разбираться на месте: логи в ELK
  всё равно живут только в рамках текущей сессии.
- Kibana не открылась — не беда, весь курс проходится и без неё.
