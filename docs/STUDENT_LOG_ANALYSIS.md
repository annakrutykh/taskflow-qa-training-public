# Работа с логами и Redis (Kibana, redis-cli) — необязательные, но полезные инструменты

⚠️ **Ни Kibana, ни redis-cli не обязательны для прохождения курса.** Всё
обучение можно пройти через Swagger, Postman, PostgreSQL и сам API — без
единого захода в эти инструменты. Этот документ — для тех, кто хочет
попробовать то, чем реально пользуются QA/DevOps в компаниях для
расследования инцидентов: искать не "что вернул мой запрос", а "что вообще
происходило на сервере и в его вспомогательных хранилищах".

---

## 1. Что логируется

Каждый HTTP-запрос к API пишется одной строкой в structured-JSON формате и
уходит в Elasticsearch. Поля:

| Поле | Значение |
|---|---|
| `timestamp` / `@timestamp` | время события |
| `correlationId` | request ID (UUID) — тот же, что в заголовке ответа `X-Request-ID` и в теле любой ошибки |
| `level` | `INFO` / `WARNING` / `ERROR` |
| `logger` | какой логгер записал (`app.request` — почти всегда) |
| `message` | текст сообщения (`"request completed"` для обычных запросов) |
| `method` | HTTP-метод |
| `path` | путь ручки |
| `statusCode` | код ответа |
| `durationMs` | время обработки в миллисекундах |
| `clientIp` | IP клиента |
| `userId` | id авторизованного пользователя (если есть) |
| `username` | email авторизованного пользователя (если есть) |

Правило простое: `level` зависит от `statusCode` — `2xx/3xx` → `INFO`, `4xx`
(включая `401`, `404`, `422`, `429`) → `WARNING`, `5xx` и необработанные
исключения → `ERROR`. Отдельного поля "тип события" нет — успешная
регистрация это просто `POST /api/v1/auth/register` со `statusCode: 201`,
неуспешный логин — `POST /api/v1/auth/login` со `statusCode: 401`, и т.д.
Это реалистично: в реальных системах вы точно так же ищете события по
методу/пути/коду, а не по готовым ярлыкам.

### Логируется абсолютно каждый запрос — включая открытие Swagger

Логируется не только то, что вы явно тестируете, а вообще любой HTTP-запрос
к API, без исключений. Из-за этого, ещё до вашего первого "настоящего"
тестового запроса, в логах уже будет несколько строк — просто от открытия
`http://localhost:8000/docs` в браузере: сама страница (`GET /docs`) плюс
запрос, которым Swagger UI сам подгружает схему для отрисовки
(`GET /openapi.json`). Это ожидаемо, не повод искать "откуда взялись чужие
запросы".

### Логи не постоянны

Логи живут только в рамках текущей сессии стенда:

- `docker compose down -v` очищает их полностью (как и Redis, и PostgreSQL).
- `POST /api/v1/admin/reset` их **не трогает** — он чистит только
  PostgreSQL, Elasticsearch не затрагивает: старые записи в Kibana останутся
  видны даже после сброса данных в БД.

## 2. Как открыть Kibana

1. Убедитесь, что стек поднят: `docker compose up --build` (или `-d`).
2. Откройте в браузере `http://localhost:5601`. Логин/пароль вводить не
   нужно — авторизация в Kibana в этом стенде отключена
   (`xpack.security.enabled: false`), сразу попадаете на главный экран.
3. **Первый запуск стека может занимать до 1-2 минут**, пока Elasticsearch и
   Kibana инициализируются — если видите ошибку сразу после `docker compose
   up`, подождите и обновите страницу.

### Первоначальная настройка (один раз)

1. Слева откройте меню (☰) → **Discover**.
2. Если попросит создать **Data View** — в форме два разных поля, не
   перепутайте:
   - **Name** — произвольное название для себя, на поиск не влияет.
   - **Index pattern** — сюда вводите именно `taskflow-logs-*`, **со
     звёздочкой на конце** (wildcard: без неё индексы с датой в имени не
     найдутся).

   Поле времени (**Timestamp field**) — `@timestamp`.
3. Готово — теперь видно все логи за всё время работы текущей сессии
   (данные не переживают `docker compose down -v`, см. README).

### Как найти нужный лог — по шагам

Сразу после настройки таблица показывает все записи за сессию, отсортированные
по времени (новые сверху), но у каждой строки видно только два столбца —
`Time` и `Document` (он же `_source`, весь JSON целиком). Чтобы посмотреть
конкретную запись:

1. Слева от строки есть стрелочка `>` — нажмите, строка развернётся и
   покажет все поля лога (`level`, `statusCode`, `method`, `path` и т.д.)
   по отдельности.
2. Если записей много — сначала сузьте выборку через строку поиска над
   таблицей (см. раздел 3 ниже), потом уже разворачивайте нужную строку.
3. Если таблица вообще пустая — значит с момента настройки Data View не
   было ни одного запроса к API: сделайте пару запросов через Swagger и
   обновите страницу (иконка ⟳ рядом со строкой поиска).

### Полезные столбцы в таблице

Разворачивать каждую строку неудобно, когда логов много — вместо этого
можно вывести нужные поля отдельными столбцами:

1. Слева от таблицы — панель **Available fields** со строкой поиска над
   ней. Введите туда, например, `level`.
2. Наведите курсор на найденное поле `level` — справа от названия
   появится значок **+**. Нажмите его — столбец `level` добавится в
   таблицу.
3. Повторите для `statusCode`, `method`, `path` — получится компактная
   сводная таблица вместо разворачивания каждой строки по отдельности.
4. Заголовки столбцов можно перетаскивать (drag), чтобы поменять порядок.
   Чтобы убрать столбец — та же кнопка у поля в панели слева станет
   значком **−**.

## 3. Как искать

Строка поиска в Discover понимает простой синтаксис `поле:значение`, можно
комбинировать через `AND`/`OR`.

| Задача | Запрос в Discover |
|---|---|
| Все запросы | (оставить поле поиска пустым) |
| Ошибки 500 | `statusCode:500` |
| Ошибки 404 | `statusCode:404` |
| Ошибки 401 | `statusCode:401` |
| Rate limit (429) | `statusCode:429` |
| Все ошибки клиента | `statusCode >= 400 and statusCode < 500` |
| Все ошибки сервера | `statusCode >= 500` |
| Запросы конкретного пользователя | `userId:5` или `username:"ivan@example.com"` |
| Неуспешные попытки входа | `path:"/api/v1/auth/login" and statusCode:401` |
| Конкретный запрос по request_id | `correlationId:"<значение из X-Request-ID>"` |
| Необработанные исключения | `logger:"app.error"` |
| Медленные запросы | `durationMs > 500` (порог — пример, подберите свой) |

Чтобы найти `correlationId` для конкретного запроса — возьмите значение
заголовка `X-Request-ID` из ответа (виден в Swagger/Postman/`curl -i`) или
из тела любой ошибки (поле `correlationId`).

## 4. Учебные задания

Выполните после того, как сгенерируете себе трафик через Swagger/Postman
(десяток-другой разных запросов, включая намеренно "плохие"):

1. **Найдите все ваши неуспешные попытки входа** за сессию — сколько их и
   с какими email вы пытались войти?
2. **Спровоцируйте `429`** (несколько быстрых запросов подряд на
   `/auth/login`) и найдите этот момент в логах — сколько запросов прошло
   до блокировки?
3. **Возьмите `X-Request-ID`** из любого ответа с ошибкой `4xx` и найдите
   именно эту запись по `correlationId` — совпадают ли `method`/`path` с
   тем, что вы реально отправляли?
4. **Найдите самый медленный запрос** за сессию (сортировка по
   `durationMs`) — какая это ручка и логично ли, что она самая медленная?
5. **Посчитайте**, сколько всего запросов сделал конкретный пользователь
   (`userId`) — воспользуйтесь количеством строк в Discover после фильтра.
6. (Продвинутое) Найдите в логах побочный эффект одного из ваших багов
   из `docs/STUDENT_BUG_REPORTING.md` — например, лишнее поле, странный
   код ответа или подозрительное содержимое `message` — это тоже
   допустимое доказательство в баг-репорте, приложите скриншот/выдержку.

## 5. Если Kibana не открывается

- Дайте ей 1-2 минуты после `docker compose up` — Elasticsearch и Kibana
  стартуют дольше, чем API/PostgreSQL.
- `docker compose ps` — `elasticsearch` и `kibana` должны быть `Up`.
- Если что-то пошло не так — проще всего `docker compose down -v` и
  `docker compose up --build` заново, чем разбираться на месте: логи в ELK
  всё равно живут только в рамках текущей сессии.
- Kibana не открылась — не беда, весь курс проходится и без неё.

## 6. Redis: как посмотреть rate limit и blacklist своими глазами

### Зачем тут вообще Redis

Redis в проекте — не альтернатива PostgreSQL и не хранилище логов, а место
для **короткоживущих** данных, которым не место в реляционной БД, потому
что они должны сами "сгорать" по времени (TTL). Так же используют Redis
и в реальных компаниях — как быструю прослойку рядом с основной БД, а не
замену ей. В проекте три сценария:

- **Rate limiting** — счётчик попыток на определённое действие (например,
  вход) за окно времени. Как только окно истекает, счётчик сам исчезает.
- **Blacklist токенов** — после `logout` сам JWT-токен ещё технически
  валиден до истечения срока действия, поэтому его идентификатор кладётся
  в Redis с TTL, равным оставшемуся сроку жизни токена — и на каждый запрос
  сверяется "не в блэклисте ли он".
- **Кэширование** — ответ `GET /projects/{id}` кладётся в Redis на
  короткое время, чтобы повторные запросы не каждый раз шли в PostgreSQL.
  Это самый частый сценарий использования Redis на реальных проектах
  (кэш-прослойка перед БД для "горячих" данных), см. раздел 7 ниже.

Контракт rate limiting и blacklist — `docs/API_SPEC.md`, раздел 6.1 (Auth),
включая fail-open поведение при недоступности Redis (у кэша — то же
fail-open: недоступность Redis не должна возвращать ошибку, запрос просто
идёт напрямую в БД).

### Как зайти в redis-cli

```bash
docker compose exec redis redis-cli
```

Приглашение терминала изменится на `127.0.0.1:6379>` — вы внутри Redis,
дальше команды вводятся прямо туда, без `docker compose`.

### Как посмотреть ключи

Redis пуст, пока вы не сгенерировали активность. В отдельном окне
терминала (это оставьте открытым) сделайте через Swagger/Postman:
несколько неуспешных попыток входа подряд — для rate limit; успешный вход
и `POST /api/v1/auth/logout` — для blacklist. Затем в `redis-cli`:

```
KEYS *
```

Должны появиться ключи вида `rate_limit:<действие>:<ip>` и
`blacklist:<jti>`. Дальше по конкретному ключу (**без кавычек** —
`KEYS *` печатает их в кавычках, но вставлять нужно без них):

```
TYPE rate_limit:login:172.18.0.1
GET rate_limit:login:172.18.0.1
TTL rate_limit:login:172.18.0.1
```

`TYPE` полезен как первая проверка: если ответ `string` — `GET`/`TTL`
обязаны сработать; если `none` — ключ уже не существует (TTL истёк или
опечатка в имени). `TTL` показывает, сколько секунд осталось до
автоматического удаления ключа — так наглядно видно, что это именно
"самоочищающееся" хранилище, а не постоянная запись.

Выйти из `redis-cli`:

```
exit
```

### GUI-альтернатива: Redis Commander

Кроме `redis-cli`, ключи можно посмотреть в браузере — в стеке уже поднят
**Redis Commander**: `http://localhost:8081`. Там видно то же самое (список
ключей, `TYPE`, `TTL`, значение), только без консольных команд.

В реальных компаниях тестировщики и разработчики для Redis чаще пользуются
**RedisInsight** — официальным GUI от Redis Ltd, с графиками и
профилированием. Для курса мы взяли более лёгкий **Redis Commander**: он
не грузит систему лишним процессом и хватает его ровно для того, что нужно
на этом этапе — посмотреть ключ, тип, TTL. Это осознанный компромисс в
пользу лёгкости, а не то, что вы обязательно увидите "как есть" на реальном
проекте — там будет RedisInsight или похожий полнофункциональный инструмент.

#### Как читать интерфейс

Слева — дерево ключей, справа — карточка выбранного ключа. Соответствие
командам `redis-cli`, которые уже встречались выше:

| В интерфейсе | Аналог в `redis-cli` |
|---|---|
| Дерево ключей слева (ключи с `:` в имени сгруппированы в "папки" — `rate_limit` → `login` → `<ip>`) | `KEYS *` |
| Клик по ключу → строка **Type** в открывшейся карточке | `TYPE <ключ>` |
| Поле **Value** в карточке | `GET <ключ>` |
| Поле **TTL** в карточке (+ кнопки изменить/снять) | `TTL <ключ>` |
| Кнопка-корзина в карточке | `DEL <ключ>` |
| Значок ⟳ над деревом | повторный `KEYS *`, если список устарел |

Ключ не появится в дереве сам по себе — как и в `redis-cli`, сначала нужно
сгенерировать активность через Swagger/Postman (см. примеры выше и раздел
7 про кэш), потом обновить дерево значком ⟳.

**Практическое применение кнопки-корзины:** если во время тестирования
`/auth/login` словили `429` не по делу (например, счётчик забился
проверками невалидных тел запроса, а не реальным перебором пароля) —
не обязательно ждать `Retry-After` секунд. Найдите
`rate_limit:login:<ваш IP>` и удалите его — лимит снимется сразу же. То же
самое в `redis-cli`: `DEL rate_limit:login:<ваш IP>`.

### Учебные задания

1. Спровоцируйте rate limit на логине и посмотрите в `redis-cli`, как
   растёт счётчик попыток при каждом новом запросе.
2. Сравните значение `TTL` сразу после первой неуспешной попытки и через
   несколько секунд — убедитесь, что оно уменьшается, а не сбрасывается.
3. Сделайте `logout`, найдите соответствующий ключ `blacklist:*` и
   попробуйте выполнить запрос с уже отозванным токеном — сопоставьте
   результат с TTL ключа в Redis.

### Если redis-cli не отвечает

- `docker compose ps` — сервис `redis` должен быть `Up`.
- `KEYS *` возвращает пусто сразу после `docker compose up` — это
  нормально, ключи появляются только после реальных запросов к API.
- Полный сброс (`docker compose down -v`) очищает и Redis — как и логи,
  это данные одной учебной сессии, не постоянное хранилище.

## 7. Redis как кэш: `GET /projects/{id}`

### Как это работает

Это самый частый в индустрии сценарий использования Redis — кэш-прослойка
перед основной БД (**cache-aside**: сначала смотрим в кэш, при промахе
идём в БД и кладём результат в кэш на будущее):

1. `GET /projects/{id}` сначала смотрит в Redis по ключу
   `cache:project:<id>`.
2. Если ключа нет — данные читаются из PostgreSQL и кладутся в Redis с
   TTL **30 секунд**.
3. Проверка прав доступа (участник ли вы проекта) выполняется **при
   каждом запросе заново**, независимо от того, откуда взяты данные
   проекта — кэш не может стать способом обойти права доступа.
4. `PATCH /projects/{id}` и `DELETE /projects/{id}` явно удаляют ключ
   кэша — следующий `GET` после изменения гарантированно вернёт свежие
   данные, не дожидаясь TTL.

### Как посмотреть

```
GET cache:project:5
TTL cache:project:5
```

(или то же самое в Redis Commander — `http://localhost:8081`, ключ будет
виден в списке сразу после первого `GET` проекта).

### Учебные задания

1. Сделайте `GET /projects/{id}` дважды подряд — убедитесь, что ключ
   `cache:project:<id>` появляется в Redis после первого запроса и его
   `TTL` не превышает 30 секунд.
2. Измените проект через `PATCH /projects/{id}` и сразу проверьте
   `redis-cli GET cache:project:<id>` — ключ должен исчезнуть (или сразу
   же появиться заново со свежими данными, если успели сделать `GET`
   между `PATCH` и проверкой).
3. Подождите больше 30 секунд, ничего не меняя, и проверьте `TTL` — ключ
   должен исчезнуть сам по себе.
4. (Продвинутое) Прогрейте кэш проекта одним пользователем (`GET`), затем
   запросите тот же `project_id` токеном пользователя, который не состоит
   в проекте — ожидаемо `404`, несмотря на прогретый кэш: это проверка
   того, что права доступа не читаются из кэша вместе с данными.
