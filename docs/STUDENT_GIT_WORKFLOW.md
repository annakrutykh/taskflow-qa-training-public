# Работа с Git в рамках курса

## 1. Как устроен репозиторий курса

Вы работаете с публичным репозиторием курса — отдельным от внутреннего репозитория
преподавателя, где ведётся основная разработка платформы. В репозитории курса нет
истории коммитов, инструкторских заметок или служебных данных — только рабочий код
и документация, актуальные на момент публикации.

## 2. Рекомендуемая модель: Fork

Мы используем модель **Fork + собственный репозиторий студента**:

1. Откройте репозиторий курса на GitHub (ссылку даст преподаватель).
2. Нажмите **Fork** — у вас появится собственная копия репозитория в вашем аккаунте,
   полностью независимая: пуш в свой форк не затрагивает оригинал.
3. Склонируйте **свой форк** (не оригинал):

```bash
git clone <ссылка на ВАШ форк>
cd <название-папки-проекта>
```

4. Добавьте оригинальный репозиторий курса как `upstream` — источник обновлений:

```bash
git remote add upstream <ссылка на оригинальный репозиторий курса>
git remote -v   # проверить: origin — ваш форк, upstream — репозиторий курса
```

## 3. Получение обновлений от преподавателя

Если преподаватель опубликовал обновления (новое задание, исправление окружения):

```bash
git fetch upstream
git checkout main
git merge upstream/main
```

Если у вас есть незакоммиченные локальные изменения и `merge` конфликтует — сначала
сохраните свою работу (`git add` + `git commit` или `git stash`), затем повторите merge.

## 4. Создание собственной feature-ветки

Не работайте с багрепортами и заметками прямо в `main` — создайте свою ветку:

```bash
git checkout -b bugreports/<ваше-имя-или-инициалы>
```

Складывайте туда: файлы с найденными баг-репортами (например,
`bugreports/BUG-AK-01.md`, по шаблону из `docs/STUDENT_BUG_REPORTING.md`), собственные
тесты, заметки. Коммитьте с понятными сообщениями:

```bash
git add bugreports/BUG-AK-01.md
git commit -m "docs: баг-репорт BUG-AK-01 — расхождение в сортировке задач"
git push origin bugreports/<ваше-имя-или-инициалы>
```

## 5. Как сдавать найденные дефекты

Оформите каждый баг-репорт отдельным файлом по шаблону
`docs/STUDENT_BUG_REPORTING.md` в своей ветке `bugreports/...`, затем откройте
**Pull Request** из этой ветки в `main` вашего же форка (не в репозиторий
преподавателя — PR в оригинал не нужен и не будет ожидаться) и отправьте
преподавателю ссылку на PR (или на ваш форк — как договоритесь на курсе).
Преподаватель проверяет баг-репорты в вашем форке, PR сливать не обязательно.

## 6. Общие рекомендации по git

- Коммитьте небольшими логическими порциями, а не одним огромным коммитом в конце.
- Пишите сообщения коммитов по смыслу изменения ("что и зачем"), а не "fix", "wip", "2".
- Не переписывайте историю (`git rebase -i`, `git push --force`) в ветках, которые уже
  отправляли преподавателю — это затрудняет проверку.
- Перед тем как начать новое задание — проверьте `git fetch upstream` и обновитесь
  (раздел 3), чтобы работать с актуальной версией.

## 7. Почему выбрана именно такая модель (для интересующихся)

Для распространения учебного материала рассматривались три подхода:

| Подход | Плюсы | Минусы |
|---|---|---|
| **Fork публичного репозитория курса** *(выбран)* | Каждый студент получает независимый репозиторий; есть встроенный механизм обновлений через `upstream`; сдача работы — стандартный Pull Request, знакомый по реальным проектам | Нужно самостоятельно донастроить `upstream` (один раз, см. раздел 2) |
| **GitHub Template Repository** | Тоже независимая копия без общей истории с оригиналом | Нет встроенной связи с исходным репозиторием — обновления от преподавателя пришлось бы раздавать вручную (патчи/архивы), а не через `git pull` |
| **Один общий приватный репозиторий с веткой для студентов** | Проще всего в настройке (одна ветка вместо форков) | Все студенты пишут в одну и ту же историю — конфликты веток, сложно давать индивидуальную обратную связь; при полном доступе к репозиторию через git-историю можно узнать больше, чем задумано программой курса |

Fork даёт то же обучение реальному рабочему процессу (fork → feature-ветка → PR), которое
используется в большинстве open-source и корпоративных проектов, и при этом сохраняет
удобный путь получения обновлений через `upstream`.
