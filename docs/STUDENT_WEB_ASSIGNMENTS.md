# Задания по этапам — тестирование веб-клиента TaskFlow

Этот документ — только для ветки `web`. Он не заменяет `docs/WEB_SPEC.md`
(эталон поведения) и `docs/STUDENT_BUG_REPORTING.md` (как оформлять
багрепорт) — использует их обоих на каждом этапе.

Идти по порядку: каждый следующий этап опирается на то, что вы узнали на
предыдущем. Не пропускайте этапы, даже если кажется, что уже всё понятно —
критерии готовности как раз для того, чтобы это проверить.

Тестовые аккаунты и запуск — `~/Desktop/TaskFlow-С-чего-начать.html`
(или README.md).

---

## Этап 1 — Знакомство с приложением

**Цель:** понять, что вообще есть в приложении, прежде чем тестировать
что-то целенаправленно.

**Что делать:**
- Зайдите по очереди под каждым тестовым аккаунтом (обычный `USER` и
  `ADMIN` — разница в правах видна почти сразу, см. шапку сайта).
- Пройдитесь по всем пунктам меню и откройте каждый экран минимум один раз:
  «Мои проекты», страница конкретного проекта (участники + задачи),
  карточка задачи, «Мои задачи», «Профиль», «Администрирование» (только
  под `ADMIN`).
- Для себя (сдавать не нужно) зафиксируйте: маршрут → что видно на экране →
  какие кнопки есть.

**Критерии готовности:**
- [ ] Можете перечислить по памяти все экраны приложения.
- [ ] Понимаете разницу между «Мои проекты» и «Мои задачи» (это не одно и
  то же — почему?).
- [ ] Можете сказать, чем отличается то, что видит `USER`, от того, что
  видит `ADMIN`, не подглядывая в документ.

## Этап 2 — Первый сквозной сценарий

**Цель:** пройти один полный пользовательский путь от начала до конца, не
ломая ничего специально — просто чтобы увидеть, как части приложения
связаны друг с другом.

**Что делать:** пройдите сценарий целиком, шаг за шагом, записывая, что
получилось на каждом шаге:

1. Зарегистрируйте нового пользователя.
2. Создайте проект.
3. Добавьте в проект участника — можно кого-то из тестовых аккаунтов
   (например, `anna@example.com`).
4. Создайте задачу в этом проекте.
5. Назначьте на неё исполнителя.
6. Смените статус задачи.
7. Оставьте комментарий к задаче.

**Критерии готовности:**
- [ ] Сценарий пройден целиком, есть короткий протокол «шаг → что
  увидели» хотя бы в свободной форме (заметка, не обязательно багрепорт).
- [ ] Если на каком-то шаге поведение не совпало с ожиданием — отдельно
  отмечено, но пока не оформлено как баг (это будет на этапе 6).

## Этап 3 — Ролевая матрица

**Цель:** увидеть своими глазами, как один и тот же экран выглядит и
ведёт себя для разных ролей — это ядро тестирования приложения с
ролевой моделью.

**Что делать:** откройте `docs/WEB_SPEC.md`, раздел 3.2 (таблица ролей
участника проекта). Возьмите один проект (свой из этапа 2, или проект
`TaskFlow Backend` из сида — там уже есть все три роли: `ADMIN` —
владелец, `Иван Иванов` — менеджер, `Анна Петрова` — наблюдатель).
Залогиньтесь под каждым участником по очереди и для каждого проверьте
минимум 5 действий из таблицы — например:

- Виден ли «Редактировать» проект?
- Виден ли «Добавить участника»?
- Виден ли «Создать задачу»?
- Можно ли сменить статус чужой задачи?
- Можно ли удалить чужой комментарий?

**Критерии готовности:**
- [ ] Заполнена реальная (не переписанная из спеки, а именно
  пронаблюдённая) таблица «роль × действие» минимум на 5 действий для
  минимум 3 ролей.
- [ ] Явно зафиксировано: либо «всё совпало с `WEB_SPEC.md`», либо
  указано конкретное расхождение (роль/действие/что увидели вместо
  ожидаемого).

## Этап 4 — Валидация и пустые состояния

**Цель:** проверить границы — обязательные/необязательные поля, длину
значений, что происходит, когда список пуст.

**Что делать:**
- Откройте сводную таблицу валидации в `docs/WEB_SPEC.md`, раздел 7.
  Для каждого поля попробуйте нарушить правило: оставить пустым (если
  обязательно), ввести значение длиннее лимита, ввести некорректный
  формат (email, несовпадающие пароли).
- Найдите минимум два «пустых состояния» (например: только что созданный
  проект без задач, отфильтрованный список без результатов) и сверьте
  текст/поведение с разделом 5 `docs/WEB_SPEC.md`.

**Критерии готовности:**
- [ ] Проверено минимум 8 правил валидации из таблицы, для каждого
  зафиксировано фактическое поведение.
- [ ] Найдено и описано минимум 2 пустых состояния.

## Этап 5 — Инварианты и межролевые сценарии

**Цель:** самые сложные сценарии курса — те, что требуют координации
нескольких аккаунтов или последовательности действий, а не одного клика.
Раздел 8 `docs/WEB_SPEC.md` — весь список, для этапа возьмите минимум 3
пункта на выбор, например:

- Последний активный `ADMIN` — нельзя разжаловать/деактивировать/удалить.
- Не больше 3 активных `ADMIN` одновременно.
- Последний `OWNER` проекта — нельзя разжаловать/удалить, пока не
  назначен другой.
- Исполнитель задачи без членства в проекте — видит задачу и «Мои
  задачи», но не саму страницу проекта.
- `VIEWER`, назначенный исполнителем своей задачи — может менять статус,
  но не более того.

**Что делать:** для каждого выбранного пункта — специально
воспроизведите ситуацию (может понадобиться несколько тестовых
аккаунтов и вкладок браузера одновременно) и зафиксируйте: получилось ли
поведение таким, как описано.

**Критерии готовности:**
- [ ] Выбрано и проверено минимум 3 инварианта.
- [ ] Для каждого — шаги воспроизведения и результат (совпало/не
  совпало с `WEB_SPEC.md`).

## Этап 6 — Целенаправленный поиск дефектов и багрепорт

**Цель:** применить всё предыдущее не по чек-листу, а свободно — найти
то, что не попало ни в один из предыдущих этапов.

**Что делать:** 1–2 часа свободного тестирования. Идеи, с чего начать:
- Быстрые повторные клики по одной и той же кнопке (двойная отправка).
- Одновременная работа под двумя разными аккаунтами в двух вкладках —
  что происходит с данными в реальном времени.
- Ввод в поля явно «неправильных» значений: HTML-теги, очень длинные
  строки, эмодзи, пробелы вместо текста.
- DevTools → вкладка Network — смотрите, что реально уходит на сервер
  и что приходит в ответ, даже если в интерфейсе всё выглядит гладко.
- Навигация вперёд/назад браузером посреди заполнения формы.

**Критерии готовности:**
- [ ] Оформлен минимум один багрепорт по шаблону из
  `docs/STUDENT_BUG_REPORTING.md` (с поправкой на веб — шаги в
  интерфейсе и скриншот вместо запроса/ответа, см. раздел 3 того
  документа) и отправлен так, как договорились с преподавателем.
- [ ] Если за всё время дефектов не нашлось — вместо багрепорта
  подготовлен короткий список того, что проверяли, и почему уверены,
  что расхождений нет. «Не нашёл ничего» без объяснения, что именно
  проверяли, не считается выполненным этапом.
