# Как тестировать HTTP-методы

Универсальный чек-лист для тест-дизайна при работе с любым REST API — не
привязан к конкретному проекту и не содержит готовых тест-кейсов. Используйте
его как отправную точку, чтобы самостоятельно сформулировать проверки для
конкретной ручки, опираясь на её спецификацию.

---

## GET

- [ ] **Успешное получение** — данные приходят в ожидаемом виде при валидном запросе.
- [ ] **Несуществующий объект** — что возвращается, если запрашиваемого ресурса нет.
- [ ] **Фильтрация** — поведение при валидных, невалидных, пустых и комбинированных значениях фильтров.
- [ ] **Сортировка** — по каким полям возможна, поведение при неизвестном поле сортировки, направление (asc/desc).
- [ ] **Пагинация** — границы (первая/последняя страница, за пределами диапазона), значения по умолчанию, некорректные `limit`/`offset`.
- [ ] **Пустой результат** — как выглядит ответ, когда данных нет вообще или нет после фильтрации.
- [ ] **Структура ответа** — соответствие контракту (обязательные поля, типы, формат, обёртка списка).
- [ ] **Корректность данных** — соответствуют ли значения в ответе тому, что реально хранится.
- [ ] **Авторизация** — поведение с валидным токеном, без токена, с невалидным/просроченным токеном.
- [ ] **Права доступа** — видимость данных в зависимости от роли/владения ресурсом.
- [ ] **Статус-коды** — соответствие кода ответа документированному поведению для каждого сценария выше.
- [ ] **Производительность** — время ответа на типичном и на большом объёме данных.
- [ ] **Анализ логов** — что записывается в лог при успешном и неуспешном запросе.

---

## POST

- [ ] **Успешное создание** — ресурс создаётся, ответ содержит ожидаемые данные.
- [ ] **Обязательные поля** — поведение при их отсутствии, по отдельности и в комбинации.
- [ ] **Необязательные поля** — поведение при их наличии/отсутствии, значения по умолчанию.
- [ ] **Типы данных** — поведение при несоответствии ожидаемому типу поля.
- [ ] **Ограничения значений** — границы допустимых диапазонов, значения на границе и за ней.
- [ ] **Длина строк** — минимальная/максимальная длина, пустая строка, значения на границе.
- [ ] **Формат данных** — поля с ожидаемым форматом (даты, email и т.п.) при валидном и невалидном формате.
- [ ] **Отсутствие body** — поведение при пустом теле запроса.
- [ ] **Отсутствие обязательных полей** — сообщение и код ошибки.
- [ ] **Лишние поля** — поведение при полях, не описанных в контракте.
- [ ] **Дублирование данных** — поведение при создании ресурса, нарушающего уникальность.
- [ ] **Повторная отправка запроса** — идемпотентность (или её отсутствие) при повторе идентичного запроса.
- [ ] **Корректность сообщения об ошибке** — понятность, соответствие единому формату ошибок, отсутствие технических деталей реализации.
- [ ] **Структура ответа** — соответствие контракту при успехе и при ошибке.
- [ ] **Статус-коды** — соответствие документированному поведению для каждого сценария.
- [ ] **Сохранение данных** — созданный ресурс реально появляется в БД в ожидаемом виде.
- [ ] **Анализ логов** — что записывается в лог при успешном и неуспешном создании.

---

## PUT / PATCH

- [ ] **Успешное изменение** — данные обновляются, ответ отражает изменения.
- [ ] **Изменение отдельных полей** — частичное обновление (особенно для PATCH) не затрагивает остальные поля.
- [ ] **Изменение всех полей** — полное обновление (особенно для PUT) — что происходит с полями, не переданными в запросе.
- [ ] **Обновление несуществующего объекта** — код и сообщение ошибки.
- [ ] **Пустые значения** — поведение при попытке обнулить поле (и отличие "поле не передано" от "поле передано как пустое/null").
- [ ] **Ограничения полей** — те же границы значений/длины/формата, что и при создании, но в контексте обновления.
- [ ] **Формат данных** — валидация формата обновляемых полей.
- [ ] **Отсутствие обязательных данных** — если метод требует определённый набор полей — поведение при их нехватке.
- [ ] **Сохранение изменений** — изменения переживают повторное чтение ресурса.
- [ ] **Проверка БД** — фактическое состояние записи в БД соответствует ответу API.
- [ ] **Анализ логов** — что записывается в лог при успешном и неуспешном обновлении.

---

## DELETE

- [ ] **Успешное удаление** — ресурс удаляется, соответствующий код ответа.
- [ ] **Повторное удаление** — поведение при повторном вызове на уже удалённый ресурс.
- [ ] **Удаление несуществующего объекта** — код и сообщение ошибки.
- [ ] **Удаление без авторизации** — поведение без токена/с невалидным токеном.
- [ ] **Удаление чужого объекта** — поведение при отсутствии прав на конкретный ресурс.
- [ ] **Влияние на связанные данные** — что происходит со связанными сущностями (каскад, блокировка, "осиротевшие" записи).
- [ ] **Проверка удаления в БД** — фактическое состояние записи (физическое или логическое удаление) после операции.
- [ ] **Анализ логов** — что записывается в лог при удалении.
- [ ] **Статус-коды** — соответствие документированному поведению для каждого сценария выше.

---

Этот документ — справочный чек-лист, а не замена анализу требований и
спецификации конкретного API. Прежде чем применять пункты чек-листа к
реальной ручке, сверьтесь с её описанием — не любая проверка из списка
применима к любому эндпоинту, и не любой пункт списка исчерпывает все
проверки, нужные именно для него.
