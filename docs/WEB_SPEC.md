# WEB_SPEC.md — Спецификация веб-клиента TaskFlow

> Целевое описание поведения веб-интерфейса (`web/`) — экраны, роли, права,
> валидация, состояния. Пишется с точки зрения дизайнера и аналитика: что
> должно происходить на экране, а не как это реализовано в коде.

## 1. Как использовать этот документ

Веб-клиент — отдельный трек курса (ветка `training-fullstack`), надстройка
над тем же API, что описан в `docs/API_SPEC.md`. В отличие от API-трека, в
вебе **нет намеренно внедрённых дефектов** (`TRAINING_DEFECTS` веба не
касается) — это рабочее приложение, и любое найденное расхождение с этим
документом является настоящим багом, а не учебной ловушкой.

Тестируйте реально запущенный веб-клиент (`http://localhost:3000`) против
описанного здесь поведения: заводите тестовые сценарии по ролям и экранам
ниже, сравнивайте фактическое поведение с ожидаемым. Формат багрепорта — тот
же, что для API: `docs/STUDENT_BUG_REPORTING.md`.

Контракт данных (поля запросов/ответов, коды ошибок) — в `docs/API_SPEC.md`,
этот документ его не дублирует, только ссылается там, где это важно для
поведения экрана.

## 2. Технические вводные

- Веб-клиент — SPA (React), обращается к тому же REST API
  (`/api/v1/...`), что и Swagger/Postman.
- Токен доступа хранится в `localStorage` браузера (переживает перезагрузку
  страницы, общий на все вкладки одного профиля браузера; НЕ переживает
  переключение на другой браузер/профиль/инкогнито).
- Все мутирующие действия идут через отдельные запросы к API — веб не имеет
  собственной бизнес-логики сверх того, что делает API; правила ниже — это
  правила самого API, отражённые в интерфейсе.
- Ошибки API (`{"error": {"code", "message", ...}}`) показываются
  пользователю как всплывающее уведомление (toast) или баннер над формой, с
  текстом `error.message` от сервера — он **на русском** (см.
  `docs/API_SPEC.md`, раздел 5). Технические поля (`code`, `correlationId`)
  в интерфейсе не показываются.

## 3. Роли и права доступа

### 3.1 Глобальные роли (`USER` / `ADMIN`)

| Что | `USER` | `ADMIN` |
|---|---|---|
| Пункт «Администрирование» в шапке | Не виден | Виден |
| Раздел «Мои проекты» | Только проекты, где есть членство | Все проекты в системе |
| Бейдж «Моя роль» в списке проектов | Реальная роль участника | Всегда «Администратор» (даже без явного членства) |
| Доступ к любому проекту/задаче | Только по членству | Всегда, независимо от членства |
| Роль в участниках любого проекта, куда его добавили | Обычная (та, что выбрали) | Всегда форсированно «Администратор» (см. 3.2) |

### 3.2 Роли участника проекта (`project_members.role`)

| Действие | `VIEWER` | `MANAGER` | `OWNER` | `ADMIN` (форсированная) |
|---|---|---|---|---|
| Просмотр проекта, задач, участников | ✅ | ✅ | ✅ | ✅ |
| Комментирование задач | ✅ | ✅ | ✅ | ✅ |
| Смена статуса **чужой** задачи | ❌ | ✅ | ✅ | ✅ |
| Смена статуса **своей** задачи (если назначен исполнителем) | ✅ | ✅ | ✅ | ✅ |
| Создание/редактирование/удаление задач | ❌ | ✅ | ✅ | ✅ |
| Привязка/отвязка меток к задаче | ❌ | ✅ | ✅ | ✅ |
| Модерация (удаление) чужих комментариев | ❌ | ✅ | ✅ | ✅ |
| Редактирование названия/описания/статуса проекта | ❌ | ✅ | ✅ | ✅ |
| Удаление проекта | ❌ | ❌ | ✅ | ✅ (как глобальный ADMIN) |
| Добавление/удаление участников, смена их ролей | ❌ | ❌ | ✅ | ✅ (как глобальный ADMIN) |

Важные особенности роли `ADMIN` в `project_members`:
- Присваивается **автоматически и принудительно**, когда в проект добавляют
  пользователя с глобальной ролью `ADMIN` — выбор роли в форме добавления
  участника при этом игнорируется.
- **Не редактируется** — в списке участников такая строка показана
  нередактируемым бейджем, без выпадающего списка смены роли, даже для
  `OWNER`.
- Реальных прав не добавляет и не отнимает: у глобального `ADMIN` и так
  максимальный доступ независимо от того, есть ли у него вообще строка в
  участниках конкретного проекта.

### 3.3 Доступ исполнителя без членства в проекте

Пользователя можно назначить исполнителем задачи, даже если он не состоит в
участниках проекта (включая глобального `ADMIN`). Такой исполнитель:

- **Не видит** страницу проекта (`/projects/:id`) — попытка открыть её
  вернёт «Проект не найден или у вас нет к нему доступа» (правильно: у него
  нет доступа к проекту в целом, только к конкретной задаче).
- **Видит** свою задачу через «Мои задачи» (`/tasks`) — она попадает в этот
  список наравне с задачами, назначенными участникам.
- Может открыть карточку задачи, посмотреть детали, **менять статус** и
  **оставлять комментарии** (включая редактирование/удаление своих).
- **Не может**: менять название/описание/приоритет/исполнителя задачи,
  удалять задачу, управлять метками, модерировать (удалять) чужие
  комментарии.

### 3.4 Права на комментарии — сводная матрица

| Действие | Автор комментария | Не-автор, роль ≥ `MANAGER` в проекте или глобальный `ADMIN` | Не-автор, `VIEWER`/исполнитель без роли `MANAGER`+ |
|---|---|---|---|
| Добавить новый комментарий | ✅ (любой с доступом к задаче) | ✅ | ✅ |
| Редактировать существующий | ✅ | ❌ | ❌ |
| Удалить существующий | ✅ | ✅ | ❌ |

Право редактирования жёстко привязано к авторству — даже `OWNER`/`ADMIN` не
может редактировать чужой комментарий, только удалить.

## 4. Карта экранов

| Маршрут | Доступ | Назначение |
|---|---|---|
| `/login` | Не авторизован | Вход |
| `/register` | Не авторизован | Регистрация |
| `/` | Любой авторизованный | Мои проекты |
| `/projects/:id` | Участник проекта любой роли или `ADMIN` | Детали проекта: участники + задачи |
| `/tasks` | Любой авторизованный | Мои задачи (кросс-проектно, `assigneeId = я`) |
| `/profile` | Любой авторизованный | Профиль |
| `/admin` | Только `ADMIN` (иначе редирект на `/`) | Пользователи / Метки / Обслуживание |

Неавторизованный переход на любой защищённый маршрут → редирект на
`/login`. Авторизованный переход на `/login` или `/register` не имеет
специальной защиты (форма отработает как обычно, но пользователь уже
залогинен — стоит проверить, что произойдёт при повторной отправке).

## 5. Экраны подробно

### 5.1 Вход (`/login`)

Поля: email, пароль (кнопка показать/скрыть).

**Валидация на клиенте** (до отправки запроса):
- Email — обязателен, должен соответствовать формату email.
- Пароль — обязателен (без проверки сложности на входе — устаревшие пароли
  тоже должны позволять войти).

**Состояния:**
- Ошибка входа (неверный email/пароль, деактивированный аккаунт) — единый
  баннер над формой с текстом ошибки от API, поля не сбрасываются, форма
  «трясётся» (визуальная обратная связь).
- Успех — редирект на `/`.

Ссылка на регистрацию — в шапке формы.

### 5.2 Регистрация (`/register`)

Поля: имя, фамилия, email, пароль, повтор пароля.

**Валидация на клиенте:**
- Имя/фамилия — обязательны, ≤ 50 символов.
- Email — обязателен, формат email.
- Пароль — 8–64 символа, обязательна хотя бы одна строчная, одна заглавная
  буква и цифра. Рядом с меткой поля — необязательный индикатор «слабый /
  средний / сильный» (косметический, не блокирует отправку и использует
  собственную шкалу, отдельную от жёсткого правила валидности).
- Повтор пароля — обязателен, должен совпадать с паролем.

**Состояния:**
- Ошибка (например, email уже занят) — баннер с текстом от API.
- Успех — пользователь **автоматически авторизуется** (не нужно отдельно
  логиниться после регистрации) и попадает на `/`.

### 5.3 Мои проекты (`/`)

Список проектов пользователя (все проекты — для `ADMIN`; проекты по
членству — для `USER`) с пагинацией (20 на страницу).

**Колонки:** название (ссылка), описание, статус (бейдж «Активен» /
«В архиве»), моя роль (бейдж).

**Заголовок:** подпись меняется по роли — «Все проекты» (`ADMIN`) или
«Проекты, в которых вы участвуете» (`USER`), плюс общее количество.

**Состояния:**
- Загрузка — строки-скелетоны.
- Пусто — иллюстрация + «Пока нет проектов» + подсказка «Создайте первый
  проект, чтобы начать заводить задачи.». Кнопки создания в самом пустом
  состоянии нет — она уже есть в шапке раздела и не дублируется (см. §6).
- Ошибка загрузки — баннер «Не удалось загрузить проекты. Попробуйте
  обновить страницу.», список не показывается.
- Пагинация — кнопки «Назад/Вперёд» показаны, если есть смысл (offset > 0
  или есть следующая страница); работают и на пустой странице (после
  удаления последнего элемента текущей страницы).

**Создание проекта** — модалка: название (обязательно, ≤ 100), описание
(необязательно, ≤ 1000). Успех → закрытие модалки, переход сразу на
страницу нового проекта.

Доступно любому авторизованному пользователю (нет ролевого ограничения на
создание проекта — создатель автоматически становится `OWNER`).

### 5.4 Детали проекта (`/projects/:id`)

#### Шапка

Название, бейдж статуса, описание (если есть). Кнопки «Редактировать» и
«Удалить» видны только тем, у кого `canManage` (роль `MANAGER`+ в проекте
или глобальный `ADMIN`); «Удалить» — дополнительно только `OWNER`/`ADMIN`
(у `MANAGER` кнопки удаления проекта нет).

**Состояния экрана целиком:**
- Загрузка — скелетоны вместо всего содержимого.
- Проект не найден / нет доступа — баннер «Проект не найден или у вас нет к
  нему доступа.» + ссылка «Ко всем проектам» (единое сообщение для обоих
  случаев — по дизайну, чтобы не палить существование чужого проекта).
- Прочая ошибка загрузки — баннер «Не удалось загрузить проект.».

#### Редактирование проекта (модалка)

Поля: название (обязательно, ≤ 100), описание (необязательно, ≤ 1000),
статус (`Активен` / `В архиве`). Доступно `MANAGER`+/`ADMIN`.

#### Удаление проекта

Двухшаговое подтверждение (модалка с явным «Удалить»). Текст предупреждения:
«Проект и все его задачи будут помечены как удалённые. Это действие можно
отменить только через прямой доступ к БД.» — то есть удаление в интерфейсе
необратимо, это soft delete на уровне API.

#### Участники

Таблица: пользователь (с бейджем «вы» у себя), роль, действия.

- Кнопка «Добавить участника» видна только `OWNER`/`ADMIN`.
- Владельцы и админ-строки показываются первыми (порядок: `ADMIN` →
  `OWNER` → `MANAGER` → `VIEWER`).
- Роль редактируется инлайн (выпадающий список) только для
  `OWNER`/`ADMIN`-наблюдателя экрана, и только у строк **не** с ролью
  `ADMIN` (см. 3.2) — такие строки всегда просто бейдж.
- Кнопка «Удалить» у строки участника — только `OWNER`/`ADMIN`.
- Удаление последнего `OWNER` проекта или смена его роли на другую —
  запрещены (ошибка от API, показывается тостом).

**Модалка «Добавить участника»:**
- Сначала выбор роли (`Наблюдатель`/`Менеджер`/`Владелец`, по умолчанию
  «Наблюдатель») — **если** позже выбранный пользователь окажется глобальным
  `ADMIN`, это поле автоматически заменяется нередактируемой надписью
  «Администратор» с пояснением, что роль форсирована.
- Поиск пользователя по имени/email (debounce, реальный запрос только после
  начала ввода). Уже добавленные участники не показываются в результатах
  поиска (клик по ним всё равно упёрся бы в ошибку «уже участник»).
- Пустое состояние поиска: «Начните вводить имя или email» (до ввода),
  «Ищем…» (запрос в процессе), «Никого не найдено» (пустой результат).
- После выбора пользователя — карточка с именем/email и кнопкой «Изменить»
  (сброс выбора).
- Кнопка «Добавить» неактивна, пока пользователь не выбран.

#### Задачи (внутри страницы проекта)

Заголовок «Задачи» + кнопка «Создать задачу» (только `MANAGER`+/`ADMIN`).

**Фильтры:** поиск по названию (debounce), статус, приоритет — сбрасывают
пагинацию на первую страницу при изменении.

**Колонки:** задача (название-ссылка + счётчик комментариев 💬 при наличии
+ описание + чипы меток), приоритет (бейдж), статус, исполнитель, действия.

**Статус задачи** редактируется инлайн (выпадающий список) для
`MANAGER`+/`ADMIN` **или** если текущий пользователь — исполнитель этой
конкретной задачи (даже при роли `VIEWER`). Остальным — только бейдж.

**Исполнитель:** имя и фамилия, либо «—» если не назначен.

**Действия «Изменить»/«Удалить»** — только `MANAGER`+/`ADMIN`.

**Состояния:**
- Загрузка — скелетоны.
- Пусто без фильтров: «Пока нет задач» + подсказка «Создайте первую задачу
  для этого проекта.», если есть право (`MANAGER`+/`ADMIN`). Кнопки создания
  в самом пустом состоянии нет — она уже есть в шапке раздела «Задачи» и не
  дублируется (см. §6).
- Пусто с активными фильтрами: «Нет задач по фильтру» (без подсказки).
- Пагинация — как в «Мои проекты», работает и на опустевшей странице.

**Модалка создания/редактирования задачи** (только `MANAGER`+/`ADMIN`):
- Название — обязательно, ≤ 100.
- Описание — необязательно, ≤ 1000.
- Приоритет — `Низкий`/`Средний`/`Высокий`, по умолчанию «Средний».
- Исполнитель — необязательное поле, поиск по всем пользователям системы
  (не только участникам проекта, включая `ADMIN` — см. 3.3), с теми же
  пустыми состояниями, что и поиск участника. Можно оставить пустым (задача
  без исполнителя) или снять выбранного через «Изменить».
- Метки — переключаемые чипы по всем существующим меткам системы (если
  меток нет — подсказка «Меток пока нет — создать можно в разделе
  «Админ».»). В режиме редактирования — предзаполнены текущими метками
  задачи.

**Удаление задачи** — двухшаговое подтверждение, текст: «Задача «…» и её
комментарии будут помечены как удалённые.».

#### Карточка задачи (открывается кликом по названию, доступна всем с доступом к задаче)

Показывает: описание, приоритет, статус, исполнитель («Не назначен», если
нет), метки (если есть) — всё в виде подписанных пар поле/значение, только
для чтения (редактирование полей задачи — только через модалку
редактирования в списке задач, `MANAGER`+/`ADMIN`).

**Комментарии** (см. матрицу прав 3.4):
- Список: автор, текст, кнопки «Изменить» (только у своих) и «Удалить»
  (у своих всегда, у чужих — только при праве модерации).
- Удаление — двухшаговое: сначала кнопка «Удалить» превращается в «Точно?»
  + «Отмена».
- Редактирование — инлайн `textarea` с кнопками «Сохранить»/«Отмена»,
  ≤ 500 символов.
- Начало редактирования одного комментария снимает «армирование» удаления
  другого (и наоборот) — на экране единовременно активно только одно
  опасное/редактируемое действие.
- Форма нового комментария внизу — `textarea` (≤ 500) + «Отправить»,
  кнопка неактивна для пустого текста.
- Пусто: «Пока нет комментариев.».

### 5.5 Мои задачи (`/tasks`)

Список задач, **назначенных лично на текущего пользователя** (не все задачи
проектов, в которых он состоит) — с теми же фильтрами (поиск/статус/
приоритет) и пагинацией, что и задачи внутри проекта.

**Колонки:** проект (название), задача (+ счётчик комментариев + метки),
приоритет, статус.

**Статус** — редактируется инлайн **всегда** (раз список и так отфильтрован
по «назначено на меня», право менять статус есть у любого исполнителя
независимо от роли в проекте).

**Карточка задачи** (по клику) — та же, что в 5.4, право на модерацию чужих
комментариев считается по **реальной роли пользователя в проекте этой
конкретной задачи** (`MANAGER`+/`OWNER`/`ADMIN`), а не универсально.

**Пусто:** «Задач пока нет» / «Нет задач по фильтру», подсказка «Задачи
появятся здесь, как только вас назначат исполнителем.».

### 5.6 Профиль (`/profile`)

Поля: email (только чтение), имя, фамилия (обе обязательны, ≤ 50), роль
(только чтение, текстовая метка «Пользователь»/«Администратор»).

Только чтение визуально отличается (блёклый фон/текст, курсор
«недоступно») — это осознанно, менять email/пароль/роль через профиль
нельзя (API этого не поддерживает).

Успешное сохранение — тост «Профиль обновлён», шапка (имя/аватар)
обновляется без перезагрузки страницы.

### 5.7 Администрирование (`/admin`, только `ADMIN`)

Три вкладки, переключение без перезагрузки данных других вкладок.

#### Вкладка «Пользователи»

Таблица всех пользователей системы с пагинацией (20 на страницу): имя +
email (с бейджем «вы» у себя), роль (выпадающий список `USER`/`ADMIN`),
статус (бейдж + кнопка «Деактивировать»/«Активировать»), «Удалить».

**Все три действия (роль/статус/удаление) недоступны для самого себя** —
администратор не может разжаловать, деактивировать или удалить собственную
учётную запись из этого экрана (кнопки задизейблены).

Инварианты, которые может вернуть API (показываются тостом, не проверяются
превентивно на клиенте):
- Нельзя понизить/деактивировать/удалить **последнего** активного `ADMIN`
  в системе.
- Нельзя повысить пользователя до `ADMIN`, если активных `ADMIN` уже 3
  (максимум).
- Нельзя удалить пользователя, если он — последний `OWNER` хотя бы одного
  (не удалённого) проекта.

Модалка удаления — предупреждение: «Пользователь «…» будет помечен как
удалённый. Если он — последний владелец какого-то проекта, удаление будет
отклонено (сначала назначьте другого владельца).».

#### Вкладка «Метки»

Форма создания (название, ≤ 30, обязательно) + список существующих меток
с двухшаговым удалением («Удалить» → «Точно удалить?» + «Отмена»).

Создание метки с уже существующим названием — ошибка от API баннером над
формой. Пусто: «Меток пока нет.».

Удаление метки физическое (не soft delete) и каскадно отвязывает её от
всех задач, где она была прикреплена.

#### Вкладка «Обслуживание»

Одна опасная кнопка — «Сбросить БД», двухшаговое подтверждение («Точно
сбросить всё?» + «Отмена»). Предупреждение в интерфейсе: полностью
очищает все данные и заново засеивает из `seed.py`, необратимо. После
успеха локальный кэш запросов приложения полностью сбрасывается (все
списки перезапросятся заново).

## 6. Сквозные UI-паттерны

- **Пагинация** — везде одинаковая: «Назад»/«Вперёд» + диапазон «X–Y из
  N», кнопки видны, если есть смысл листать (не пропадают на опустевшей
  последней странице).
- **Поиск** — везде с debounce (~250 мс), реальный запрос не летит на
  каждое нажатие клавиши.
- **Ошибки форм** — баннер над формой с текстом от API, поле-уровневая
  валидация — рядом с конкретным полем, до отправки запроса.
- **Ошибки вне форм** (мутации без своей формы: смена роли/статуса,
  удаление и т.п.) — всплывающее уведомление (toast) с текстом от API.
- **Опасные необратимые действия** (удаление проекта/участника/задачи/
  комментария/метки, сброс БД) — двухшаговое подтверждение: либо отдельная
  модалка с явной кнопкой «Удалить», либо инлайн-«армирование» кнопки
  («Удалить» → «Точно?»/«Точно удалить?» + «Отмена»).
- **Поля только для чтения** — визуально отличаются (блёклые), не просто
  задизейблены без объяснения.
- **Кнопка создания** («Создать проект» / «Создать задачу») — ровно одна на
  экран, в шапке раздела; не дублируется отдельной кнопкой в пустом
  состоянии списка, даже когда список пуст.

## 8. Инварианты и граничные случаи для целенаправленного тестирования

- Последний активный `ADMIN` в системе — нельзя разжаловать, деактивировать
  или удалить (проверить через экран «Пользователи»).
- Более 3 одновременно активных `ADMIN` — нельзя создать повышением роли.
- Последний `OWNER` проекта — нельзя разжаловать, удалить из участников или
  удалить как пользователя, пока не назначен другой `OWNER`. Отдельно
  проверить: владелец **уже удалённого** (архивного через soft delete)
  проекта удаляться обязан свободно — это не должно считаться «последним
  владельцем».
- Роль `ADMIN` участника проекта: попытка вручную назначить её обычному
  пользователю или изменить её у уже-админа — должна быть отклонена.
- Исполнитель без членства в проекте: может менять статус и комментировать
  свою задачу, но не должен суметь открыть страницу самого проекта.
- `VIEWER`, назначенный исполнителем своей же задачи: должен получить
  возможность менять статус (наравне с `MANAGER`+), но не более того.
- Смена статуса/добавление комментария к задаче из «Мои задачи» и из
  страницы проекта должны немедленно отражаться в обоих местах без ручного
  обновления страницы (общая корректность кэша).
- Токен, ставший невалидным во время работы (истёк / пользователя
  деактивировал админ / выход в другой вкладке) — специальной обработки на
  клиенте нет: следующий запрос просто вернёт ошибку `401`, которую
  конкретный экран покажет как обычную ошибку действия, автоматического
  редиректа на `/login` не произойдёт. Стоит сравнить фактическое поведение
  с ожидаемым.

## 9. Что осознанно не реализовано в вебе (не баг)

- Смена пароля и email — API это не поддерживает (`PATCH /users/me`
  принимает только имя/фамилию), поэтому в профиле таких полей нет.
- Просмотр журнала аудита (`audit_log`) — не отдаётся через API вообще, по
  дизайну курса доступен только прямым запросом к PostgreSQL.
- Просмотр логов (Kibana), Redis Commander — отдельные инструменты
  инфраструктуры, не часть веб-клиента.
