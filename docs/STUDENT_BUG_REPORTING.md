# Как искать дефекты и оформлять баг-репорт

Этот документ описывает **процесс**, а не список известных проблем — списка дефектов у вас
не будет, и это осознанно: часть задачи курса в том, чтобы находить расхождения
самостоятельно, как это делает QA-инженер на реальном проекте.

---

## 1. Как искать дефекты

У вас есть два независимых источника правды, и баг — это **расхождение между ними**:

1. **Документация** — `docs/API_SPEC.md` (контракт: коды ответов, обязательные поля,
   правила доступа, форматы) и `API_DOCUMENTATION.md`.
2. **Фактическое поведение API** — то, что реально возвращает сервис на ваш запрос.

Стратегии поиска, которые стоит комбинировать:

- **Спецификационное тестирование (spec-based).** Пройдите по `docs/API_SPEC.md` ручку за
  ручкой и для каждой проверьте: коды ответов (200/201/204, 401/403/404/422/409), формат
  тела, обязательные поля, поведение пагинации, сортировки, фильтров.
- **Ролевая матрица.** Для каждой ручки проверьте поведение под разными ролями:
  `ADMIN`, обычный `USER`-владелец, `USER`-участник с разными проектными ролями
  (`OWNER`/`MANAGER`/`VIEWER`), исполнитель задачи не из проекта, посторонний пользователь
  без доступа вообще, запрос вообще без токена.
- **Граничные значения.** Пустые строки, максимальная длина полей, отрицательные числа,
  несуществующие ID, дублирующиеся значения (email, название метки), пустые/некорректные
  тела запроса.
- **Согласованность данных.** Создайте сущность и проверьте, что она видна во всех местах,
  где должна быть видна (например: поле, добавленное к задаче, должно быть в ответе на
  `GET` этой же задачи и в списке задач).
- **Логи и побочные эффекты.** Если у вас есть доступ к логам приложения
  (`docker compose logs -f api`) — проверяйте, не улетает ли в лог что-то, чего там быть
  не должно (пароли, токены целиком).
- **Негативные сценарии.** Не только "правильный путь" (happy path) — специально ломайте
  порядок действий: удалите ресурс и обратитесь к нему повторно, отправьте запрос с
  чужим/просроченным токеном, вызовите операцию до того, как выполнены её предпосылки.

Инструменты: Swagger UI (`/docs`) для быстрых проверок, Postman-коллекция
(`postman/TaskFlow.postman_collection.json`) для сценариев из нескольких запросов, `curl`
для точного контроля заголовков и тела запроса, DBeaver — чтобы посмотреть, что реально
записалось в БД.

## 2. Что делать, когда нашли расхождение

1. **Не чините код и не открывайте PR с "исправлением".** Ваша роль — найти и описать
   дефект, а не поправить его. Это тренирует именно QA-навык.
2. **Воспроизведите ещё раз.** Прежде чем оформлять баг-репорт, повторите запрос минимум
   дважды (лучше — из чистого состояния, `POST /api/v1/admin/reset` или
   `docker compose down -v && docker compose up --build`), чтобы исключить случайность
   (гонку данных, состояние БД, опечатку в запросе).
3. **Минимизируйте сценарий.** Уберите из шагов воспроизведения всё, что не влияет на
   результат — чем короче репро, тем быстрее его можно проверить.
4. **Сверьтесь со спецификацией ещё раз.** Убедитесь, что вы правильно поняли, каким
   должно быть поведение по `docs/API_SPEC.md` — баг-репорт с неверно понятым ожидаемым
   поведением создаёт лишнюю работу на разборе.
5. Оформите баг-репорт по шаблону ниже и отправьте его так, как указано в
   `docs/STUDENT_GIT_WORKFLOW.md`.

## 3. Шаблон Bug Report

Используйте этот шаблон (скопируйте в `.md`-файл или в форму, которую укажет
преподаватель):

```markdown
# BUG-<ваши инициалы>-<порядковый номер>: <короткое название проблемы>

## Окружение
- Ветка/версия: main (commit <hash, если знаете>)
- Дата обнаружения: <YYYY-MM-DD>
- TRAINING_DEFECTS (если задавали): <значение или "не задавал(а)">

## Шаги воспроизведения
1. ...
2. ...
3. ...

## Запрос
```http
POST /api/v1/tasks HTTP/1.1
Authorization: Bearer <accessToken, при необходимости — обрежьте до первых 8 символов>
Content-Type: application/json

{
  "projectId": 1,
  "title": "..."
}
```

## Ответ (фактический)
```http
HTTP/1.1 200 OK

{
  "...": "..."
}
```

## Ожидаемое поведение
<Что должно было произойти согласно docs/API_SPEC.md — сошлитесь на конкретный раздел>

## Фактическое поведение
<Что произошло на самом деле — без интерпретаций, только факты>

## Влияние / серьёзность
<Например: блокирует основной сценарий / расхождение с контрактом, но есть обходной путь /
косметическое>

## Дополнительно
<correlationId из ответа/заголовка X-Request-ID, скриншоты, фрагмент лога — всё, что
поможет воспроизвести без лишних вопросов>
```

### Как приложить запрос и ответ

- Из Swagger: разверните запрос → "Try it out" → Execute → скопируйте блок "Curl" и блок
  "Response body" вместе с кодом ответа.
- Из Postman: кнопка "Code" на запросе даёт готовый `curl`; ответ копируйте из панели
  Response целиком (включая статус-код и заголовки, если это важно для бага).
- Из терминала: `curl -i ...` (флаг `-i` печатает и заголовки ответа, и тело) —
  перенаправьте вывод в файл (`curl -i ... > response.txt`) при желании приложить отдельно.
- **Никогда не публикуйте пароль или полный JWT-токен в баг-репорте** — если токен нужен
  для контекста, приводите только первые 8 символов (`eyJhbGciOi...`).

### Как определить expected vs actual

- **Expected** — цитата или пересказ конкретного пункта `docs/API_SPEC.md` (укажите
  раздел). Если поведение не описано явно ни в одном документе — так и напишите:
  "поведение не задокументировано, ожидание основано на общей логике REST/HTTP".
- **Actual** — только наблюдаемый факт: код ответа, точное тело, точный текст сообщения
  об ошибке. Без предположений о причине ("наверное, где-то забыли проверку") — причину
  устанавливает тот, кто будет чинить, а не вы.

## 4. Куда отправлять найденный дефект

См. `docs/STUDENT_GIT_WORKFLOW.md`, раздел про сдачу баг-репортов — там описан точный
