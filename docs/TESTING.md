# Тестовая стратегия

Три уровня — выбирайте по ситуации, не гоняйте полный набор ради опечатки в
докстринге.

| Уровень | Команда | Что входит | Тестов | Время* | Когда запускать |
|---|---|---|---|---|---|
| **Smoke** | `make smoke` | `tests/unit/` целиком + курируемый набор happy-path из `tests/integration/` (`@pytest.mark.smoke`) | 49 | ~5-10с | После каждого небольшого изменения — основной рабочий цикл |
| **Integration** | `make integration` | `tests/unit/` + весь `tests/integration/`, без e2e | 124 | ~40с | Перед пушем/PR |
| **Regression** | `make regression` | Все тесты, включая `tests/e2e/` | 125 | ~40с | Перед релизом, после крупных изменений (миграции, permissions, defects), по явной команде |

\* Время — сам pytest на прогретом образе (`docker compose build api` уже
выполнен). Без прогрева добавьте время сборки образа (`make smoke` и
остальные цели сами дергают `docker compose build api -q`, кэш делает это
почти бесплатным при отсутствии изменений в зависимостях).

```bash
make lint          # ruff + black --check, ~1-2с
make smoke         # см. таблицу выше
make integration
make regression
make test-down     # остановить db/redis, когда закончили
```

## Почему так быстро (было — не всегда)

Раньше `docker run ... pytest` каждый раз делал `pip install -r
requirements-dev.txt` внутри свежего контейнера — без персистентного
pip-кэша между запусками это добавляло от 10 до 100+ секунд на пустом
месте. Решение: `requirements-dev.txt` теперь ставится **в момент сборки
образа** (`Dockerfile`), а не при каждом запуске тестов. Да, это делает
образ `taskflow-main-api` не "чистым" prod-образом (в нём есть pytest/ruff/
black) — сознательный компромисс: это учебный проект без реального деплоя,
а разница на порядок в скорости обратной связи важнее гигиены образа.

## Защита от зависших тестов

`pyproject.toml` → `[tool.pytest.ini_options]`: `timeout = 30`,
`timeout_method = "thread"` (пакет `pytest-timeout`). Любой тест, который
выполняется дольше 30 секунд, принудительно завершается, и в выводе
явно видно, какой именно тест завис (traceback потока на момент таймаута) —
вместо того чтобы ждать pytest бесконечно.

## Smoke: что входит и почему

Курируемые happy-path сценарии, по одному-два на ключевую область,
достаточные, чтобы понять "весь стек (Postgres, Redis, авторизация, CRUD)
в принципе работает":

- регистрация, логин, доступ без токена, доступ с валидным токеном
  (`tests/integration/test_auth.py`);
- logout (проверяет и Redis-блэклист) (`tests/integration/test_rate_limit.py`);
- создание и чтение проекта (`tests/integration/test_projects.py`);
- создание и чтение задачи (`tests/integration/test_tasks.py`);
- весь `tests/unit/` (без БД, доли секунды, чистая логика — нет причин
  когда-либо его выключать).

Smoke **не** покрывает: полную ролевую матрицу, граничные значения,
намеренные дефекты, edge cases по 409/422 — за этим в `integration`/
`regression`.

### Как добавить тест в smoke

```python
import pytest

@pytest.mark.smoke
def test_something_critical(client):
    ...
```

Для целого файла (как в `tests/unit/`) — `pytestmark = pytest.mark.smoke`
на уровне модуля. Добавляйте в smoke только то, что ломает **весь**
рабочий процесс, если сломается — не превращайте smoke в дубликат
integration.

## Elasticsearch и тесты

Тесты **не** поднимают и не проверяют Elasticsearch — это отдельная,
тяжёлая инфраструктура, требование задачи прямо говорит не тащить её туда,
где без неё можно обойтись. `tests/conftest.py` выставляет
`ELASTICSEARCH_ENABLED=false` по умолчанию — `configure_logging()`
(`app/core/logging.py`) в этом случае вообще не создаёт
`ElasticsearchHandler`, приложение логирует только в stdout, как раньше.
Проверка реальной доставки логов в ES — вручную через `docker compose up`
+ Kibana (см. `docs/STUDENT_LOG_ANALYSIS.md`), не автоматизирована и не
должна быть: это интеграция с внешней системой на JSON-протоколе,
основной риск — конфигурация docker-compose, а не логика приложения.
