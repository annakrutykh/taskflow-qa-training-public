## 1. Что это за проект

**TaskFlow QA Training Platform** — система управления проектами и задачами (упрощённый аналог Jira), используемая как учебная среда для подготовки **Manual QA Engineer**.

Курс развивает навыки функционального, API-, UI- и интеграционного тестирования, работы с PostgreSQL и Redis, анализа логов (Kibana), поиска и оформления дефектов — **не автоматизацию тестирования**.

**Это ветка `web`** — расширенный трек: тот же backend, что и в API-only ветке `main`, плюс рабочий веб-клиент (`web/`) поверх него. Тестируйте оба слоя так же, как в реальном продукте компании: API — через HTTP-запросы/Swagger/Postman, интерфейс — руками через браузер по сценариям из `docs/WEB_SPEC.md`. Не читайте исходники в поисках ответа — сверяйтесь со спецификацией и наблюдайте за фактическим поведением.

## 2. Главное правило: это учебная площадка для QA

⚠️ **Часть поведения системы может намеренно отличаться от `docs/API_SPEC.md`** — это учебный материал, а не случайность.

**Ваша задача как студента — находить такие расхождения, а не исправлять их.** Если что-то выглядит как баг:
1. Не правьте код молча и не открывайте PR с «исправлением».
2. Проверьте фактическое поведение против `docs/API_SPEC.md` / `API_DOCUMENTATION.md`.
3. Оформите багрепорт по инструкции `docs/STUDENT_BUG_REPORTING.md` и отправьте преподавателю.

Если используете Claude Code или другого AI-ассистента поверх этого репозитория — тот же принцип: ассистент не должен самостоятельно «чинить» найденные расхождения без явного запроса, его задача — помогать формулировать тестовые сценарии (ручные, не код), баг-репорты и объяснять поведение API.

## 3. Документация проекта

| Документ | Содержание |
|---|---|
| `docs/API_SPEC.md` | **Целевая спецификация API.** Контракт, роли, коды ошибок, схема БД — используйте как эталон при тестировании |
| `API_DOCUMENTATION.md` | Документация по API для студентов |
| `docs/WEB_SPEC.md` | **Целевая спецификация веб-клиента** (папка `web/`) — экраны, роли, права, валидация, состояния. Эталон для тестирования веба |
| `docs/STUDENT_BUG_REPORTING.md` | Как искать расхождения с `docs/API_SPEC.md` / `docs/WEB_SPEC.md` и оформлять багрепорт |
| `docs/STUDENT_GIT_WORKFLOW.md` | Рекомендуемый процесс работы с git в рамках курса |

При расхождении фактического поведения и `docs/API_SPEC.md`/`docs/WEB_SPEC.md` — прав документ; расхождение оформляется багрепортом.

> В отличие от API-трека, у веб-клиента нет намеренно внедрённых учебных дефектов — любое расхождение с `docs/WEB_SPEC.md` является настоящим багом.

## 4. Соглашения API (пригодится при тестировании)

| Правило | Значение |
|---|---|
| Именование полей | **camelCase** в запросах и ответах |
| Списки | Всегда обёртка `{ "items": [...], "total": N, "limit": N, "offset": N, "hasNext": bool }` |
| Даты | ISO 8601, UTC, суффикс `Z` |
| Enum | СТРОКИ В ВЕРХНЕМ РЕГИСТРЕ |
| 201 Created | Обязателен заголовок `Location` |
| Ошибки | Единый формат `{ "error": { "code", "message", "details", "correlationId", "timestamp" } }` |

Полный реестр кодов ошибок (`error.code`) — `docs/API_SPEC.md`.

## 5. Автотесты и CI — не часть курса

В репозитории есть `pytest`, `Makefile`, CI — это внутренняя инфраструктура для
защиты проекта от регрессий, а не учебный материал. Вам **не нужно** писать или
запускать автотесты, изучать `pytest` — тестируйте руками через Swagger/Postman,
проверяйте данные в PostgreSQL/Redis, ищите дефекты и оформляйте баг-репорты.

В проекте действительно есть автотесты — если куратор или автотестер
попросит вас прогнать их, он даст вам конкретную команду; самостоятельно
разбираться в структуре тестов не требуется. Если такая команда понадобится
— короткая справка, как её выполнить, в `docs/TESTING.md`.
